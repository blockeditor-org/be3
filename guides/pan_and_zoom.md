Pan and zoom is a plugin capability (`capabilities.pan_and_zoom` in the manifest, see guides/adding_a_plugin_editor.md), not something an editor builds for itself. An editor with it declares that its content has a camera of its own - a world it draws at a position and a scale - and hands the camera to whatever is hosting it instead of keeping one. The point of that split is that the same editor code has to work whether it is sitting in a tab of its own or living inside another editor's canvas, without knowing which: "zoom in" means the same thing to the pixel art editor whether the person clicked its own toolbar button or turned a mouse wheel over it while it was a card on an infinite canvas, because in both cases the camera it draws through is something the host handed it, not something it owns.

## What the editor is given

The host hands the camera over as a rectangle and a scale, in the editor's own coordinates: `host.view()` / `host.view_scale()` for an egui editor, `editor.canvas()` / `editor.scale()` for a beui one, both signals the framework writes before every frame (`beui::reactive::CanvasView`, a plain `{origin, scale}`). The editor draws its content there and keeps no offset or zoom of its own - an instance never told where its view is just fills the space it has, at a scale of one, which is what happens the first frame and what happens to an editor with no camera to speak of. It moves the camera by asking rather than by touching its own state: `host.pan_view(delta)` / `editor.pan(delta)`, `zoom_view(factor, anchor)` / `editor.zoom(factor)`, and `fit_view()` / `editor.fit()`, which is what a `-`, `+` and `Fit` button call; `editor.reveal(rect)` pans a rectangle of the editor's own world into the middle of the content, which is what a jump-to-this list does. Wheel, pinch, and a middle- or space-drag over the content belong to the host as well, read once for the outermost view under the pointer, so a wheel over a block being edited inside a canvas moves the canvas rather than both; a gesture only the editor understands (dragging with a plain left click, say) it turns into a pan/zoom request of its own the same way a button does.

Because the camera is something the editor is handed rather than something it keeps, it cannot tell a tab from a canvas by looking at it, and does not need to: `pan_zoom` (`crates/editors/pan_zoom`) is the reference implementation, and its whole view is built the same way regardless of where the host puts it.

## Who owns it, and where that lives

The host side of all this is `DirectEditorViewport` and `DirectEditorTabViewport` in `crates/block-app/src/editors.rs`. `DirectEditorViewport` is rebuilt every frame: it is a queue of the pan/zoom/fit commands the editor asked for this frame, plus the `content_rect` and `scale` the editor is being told to draw at. `DirectEditorTabViewport` is the state that actually persists - a zoom float, a pan offset, and an auto-fit flag that keeps recomputing a fit-to-content scale until the user's own gesture cancels it - kept in egui's memory keyed by the editor's id, so it survives frame to frame the way a tab's scroll position would.

Which of these is authoritative for a given frame depends on how the editor was placed, and there are three cases, all going through `EditorAccess::direct_editor_frame_ui`:

- **A plain tab** (`direct_editor_tab_ui`, the top level entry point workspace_ui's own shell uses): there is no parent handing anything down, so the editor's `DirectEditorTabBands` owns both the ephemeral queue and the persisted state itself, draining the queue into the persisted zoom/pan/auto-fit every frame the way it always has.
- **A child that owns its own frame** (`own_frame_child_ui` - the workspace dock's tabs, a file-tree toolbar row, anything a parent editor places with its own chrome inside a rectangle of the parent's choosing): the parent still passes a viewport handle down, but never gives it a `content_rect`, so the child recognises it has not actually been placed on anything and falls back to computing and persisting a viewport of its own, exactly like a plain tab. This is why moving the app's own dock and tab bar into the `workspace_ui` plugin did not change how a single editor's own zoom and pan behave.
- **A focused canvas child taking over the frame** (`frame_child_ui` - an infinite_canvas-style parent promoting one of its placed children because the user focused it): the parent already knows where that child's world lands on screen - its screen rect, run through the canvas's own camera - and hands that down as an authoritative `content_rect` and `scale` on the very `DirectEditorViewport` the parent itself is about to drain. The child sees a viewport that has already been placed and defers to it completely instead of building its own: a zoom the child's own `+` button asks for and a zoom the canvas does by pinching are queued on the same object, so they are the same camera move rather than two cameras that happen to agree for a moment. `DirectEditorTabBands::outer_is_placed()` is exactly this test - "did whoever placed me already give this viewport a `content_rect`" - and everything downstream (which viewport gets drained, whose gestures get read, whose zoom persists) branches on it.

An infinite canvas applies this on its own side too: every frame it loops over the children it has placed, takes each one's queued `ViewChange`s (`Pan`, `Zoom`, `ResumeAutoFit`) and applies them straight to its own `Viewport`, the same struct that answers the canvas's own scroll and pinch gestures. `Fit` is the one exception - fitting a child means fitting that child's rect into the canvas's world, which only the canvas knows how to compute, so it is remembered as "fit this entity" and resolved the next frame instead of being applied directly. This loop is what makes the camera actually shared rather than merely handed down once: a zoom the focused child requests becomes a `ViewChange` the canvas's own viewport absorbs, which is why panning or zooming while focused into a card moves the canvas under it too.

## Drawing through it

An egui editor gets an `EditorView { rect, scale }`: `rect` is the `content_rect` translated into the frame's own local coordinates, `scale` is the camera's scale, and it is up to the editor to lay its own content out inside that rectangle at that scale (a pixel art editor divides its image's pixel size by the scale; a world with map units draws a unit that many pixels wide).

A beui editor gets a `CanvasView` and hands it straight to a `<Canvas view={...}>` node (`crates/beui/src/base/canvas.rs`). A `Canvas` does not lay its items out through the normal measure/layout pass at all - each `CanvasItem` child carries a rectangle in the editor's own world coordinates, and the canvas maps that rectangle through the view (`origin + point * scale`) to get where it paints on screen, deliberately ignoring the `Canvas` node's own laid-out rect. That is what lets an item's screen position track the shared camera exactly even though the surrounding layout (a sidebar taking width out of the frame, say) has no idea where the canvas sits on some ancestor's own canvas. Placing an item this way is not transforming it: text inside one keeps whatever size it asked for, so an editor whose content should grow with the zoom reads the scale and sizes its own text by it, the way `pan_zoom`'s cards scale their title and padding off the `scale` signal directly.

A beui editor also reports back where its content ended up. It names the node its content is in once, with `editor.content(&node_ref)`, and the framework reads that node's rectangle after every layout - the host cannot see where a beui editor put its own sidebar, so this is how it learns what rectangle to actually pan, zoom, and read wheel gestures against, which is what keeps a wheel over the sidebar from being read as a wheel over the content.

## Why the frame is bigger than the content, and why that means staying transparent

A pan-and-zoom editor is handed the *whole* ancestor frame to draw in, not a rectangle clipped down to wherever it happens to sit on the parent canvas. That is deliberate: once you are focused into an editor you need somewhere for its real chrome to live - `pan_zoom`'s sidebar is a fixed 220px, not something that could fit inside a card's own footprint - and the content itself still belongs at the position and size the shared camera says, which can be smaller than, bigger than, or only partly overlapping that footprint once you start panning and zooming while focused.

Taking the frame over resizes the editor's screen from a card's footprint to the whole frame in one step, and a plugin draws a frame behind the host: the painting the host has in hand when that happens was made for the old size. Stretching it across the new one is a visible flash of the whole editor scaled up, so the host keeps the last painting at the rectangle it was made for until the editor has painted at the new size, and the same in reverse when the frame is handed back. Nothing about that reaches the editor - it is the host holding a frame, not the editor drawing one - and it applies only to the takeover, not to an ordinary resize, where a stretched frame is a pixel or two and following the window is worth more than not distorting.

That combination only looks right if the editor paints *just* its own content and chrome and leaves everything else alone. `crates/block-ui/src/frame.rs`'s `Frame` never fills the content band itself - it only ever creates a child `Ui` sized to the content rect and calls into the editor - and the plugin framework works the same way: "a frame is transparent wherever the editor does not paint, which is what lets the layer beneath show through around a block being edited inside a canvas" (guides/adding_a_plugin_editor.md). A `Canvas` node keeps to this by construction, since its `paint` only draws its items and nothing else. The mistake this guide exists to head off is wrapping the *whole* view in an opaque background the way a normal, non-canvas editor reasonably would for its one always-solid tab: `pan_zoom` used to wrap its entire view - sidebar, rail, and stage together - in a single `<Frame color={theme.background}>`, which looked correct as a standalone tab (there is nothing to show through to) and silently painted over the entire infinite canvas underneath it the moment it was focused as a child, because the stage now spanned the whole frame rather than a small footprint. The fix was to drop that outer background and let the sidebar and rail keep their own (they already had one each, since they need to stay legible over whatever is behind them), leaving the stage - which never had a background of its own beyond that wrapper - transparent everywhere it is not actively drawing a card. A canvas-style editor should follow the same shape: give fixed chrome its own opaque background where it genuinely needs one, and never wrap the pannable/zoomable content area itself in anything that paints its full bounds solid.
