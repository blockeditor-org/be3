# Beui text

Text in beui: the base `Text` node, styled text, fonts and icons, the text area editor and rich text, and selecting read-only text. The component layers around them are in [components.md](components.md).

## The base `Text`

A base `Text` takes concrete values (a `FontId`, a colour) and knows nothing of the theme. Its children are its content, all laid out as one paragraph so wrapping, the caret and selection cross style changes:

- strings and `Prop<String>`s in the Text's own style;
- `Span`s, which override parts of the style over a run (computed runs are a `ForEach` of `Span`s);
- `Icon`s, one glyph from the icon font that holds no bytes, so the caret steps over it and copy skips it: `<Text><Icon glyph=ICON_SAVE />"Save"</Text>` copies as "Save". An icon's gap to its label is layout, not a space a selection could take;
- `TextItem`s, a child node laid out inline as one character (U+FFFC), or with `at` placed at a byte index like a caret;
- `Gap`s and `Break`s, room and line ends holding no bytes, so a soft-wrapped terminal row copies as one line. A `Gap` is `width` pixels plus a `share` of the width the text wraps at (none while it wraps nowhere, on both cores: the HTML core's share is of `--beui-gap-room`, which a `Text` sets to its width only while it wraps); a layout with a shared gap holds at the width it was laid out at alone.
- `Blank`s, a space of a given width holding one byte (a space): whitespace, so it hangs past a line's end like trailing spaces (see Wrapping) and never wraps the word before it, but past the edge it keeps its width, so a mark or glyph over it has room beside the last word. A text area's newline marker is drawn in one. The HTML core lays it out as a space in the blank's font (or the text's), its `letter-spacing` the width less the space's own advance (measured on a canvas, again when web fonts load), which the browser hangs under `pre-wrap` (an em space or an inline block would wrap); being in a real font, a mark over it is as tall as the line and a glyph over it sits on the line.

A `Span` with `isolate` is isolated for bidi, as HTML's `<bdi>`: it takes its own direction and is one neutral to the text around it, so a right-to-left name cannot carry the words beside it across itself. Text that quotes what someone typed isolates it, never with FSI/PDI characters in the string. The HTML core sets `dir="auto"` and `unicode-bidi: isolate` on the span, so the browser isolates it today; natively, layout has no bidi yet, so the run only reaches `Piece::Text::isolate` and `RichLayout::isolates`, where the bidi step of plans/deferred/i18n.md will read it.

A `Phrase` (`beui::text::Phrase`) is the same runs as a value, for a prop that takes a string: a dialog's `title` is a `Prop<Phrase>`, which takes a plain string as before. `Phrase::new().text("Leave ").quoted(name).text("?")` puts `name` in curly quotes, isolated inside them. A `Text` takes a `Phrase` (static, `Prop` or `Memo`) as content and lays out a `Span` per run, keeping them as the phrase changes; whatever needs one string (an accessibility label) joins the runs with `to_string()`.

`overflow` wraps by default (see Wrapping below); `Ellipsis` cuts each line; `Visible` lays lines out unbroken for something that scrolls or clips. There is no clip mode: cut text is `Visible` inside something that clips. `on_truncated` reports whether ellipsised text is cut, so a component can show it whole another way (a tooltip). `WrapAt::Anywhere` in a monospace font holds exactly `cols` characters a line; measure the advance as `cursor_pos(_, 1).x`, since a galley's `size()` is rounded up.

`marks` (selections), `glyphs` (centred markers such as a text area's whitespace marks) and `carets` are byte ranges over the joined content and only repaint when they change. A caret at a byte stands before the character there, past any gap, icon or break before it; at a line's end, after the last character and the gaps right after it, but before an icon (`RichLine::x_of`, and `spot` in beui-core-html's `text/web.rs`). A mark fills, a line at a time, from where a caret at its start stands to where one at its end does, so it covers the gaps inside it and is drawn exactly between its carets; a span's background covers only its own characters. The HTML core draws marks as boxes in the text's decoration (`.beui-mark`), not with CSS highlights, which paint glyphs only and would leave a gap's room bare; so do colour and decoration changes. Shaping is cached per span, and the part of a span on each wrapped line is shaped on its own rather than cut from the span's shaping, so its glyphs' subpixel phases start at the line's start and an edit earlier in the paragraph leaves later lines drawn exactly as they were. Bold and italic are synthesised by FreeType, not separate faces.

### Wrapping

Every wrapped text on the native core breaks lines by one rule, in `Builder::breakpoint` (`beui-core/src/rich.rs`), deliberately not the usual "last word that fits". The *break zone* is the last `BREAK_ZONE_EMS` (6) ems of a line's width, in the size of the `Text`'s own base font, even where a span inside it is larger. When the rest of a paragraph does not fit, the line breaks at the rightmost break point inside the zone of the best tier that has one:

1. Good: a Unicode line break opportunity (UAX #14, the `unicode-linebreak` crate): after spaces, after a hyphen before a letter, between CJK characters, and so on; also either side of a `Gap`, and the end of a piece that says `break_after`.
2. Less good: after `/ . _ : , ; ) ] } -` or before `( [ {` inside a word, for code, paths, URLs, and the ids and dates UAX #14 keeps whole because a digit follows the hyphen.
3. Last resort: any grapheme cluster boundary.

A good break point before the zone is never used: with none of tier 1 or 2 in the zone, the line breaks at the rightmost grapheme boundary that fits, a few pixels from the edge, so a long word after a short one fills the line instead of leaving the short one alone. Spaces after the last word hang, as in CSS's `pre-wrap`: a break after spaces fits when the text before them does, so the next line never starts with a space, and every line alike keeps its trailing spaces in its width while they fit and leaves them out (of its width, its alignment and the text's size) once they would overflow. A caret is kept inside the width, and a caret, selection or whitespace mark among hung spaces stops at the edge, so the marks of several hung spaces stack there. A hung `Blank` is the exception: it starts where the spaces before it stop and keeps its own width past the edge. `WrapAt::Anywhere` makes every grapheme boundary good. Nothing makes a line wider than its width: a wrapping `Text` claims no `min_width`, so a row may squeeze it, and only a grapheme wider than the whole width overflows, on a line of its own, without widening the layout (`RichLayout::size`) or any other line. Its run keeps its own size, so damage still covers the glyph.

The HTML core leaves wrapping to the browser (`overflow-wrap: break-word`, or `anywhere` for `WrapAt::Anywhere`), which breaks at the last opportunity that fits and keeps the longest word as the text's min-content width.

Each stop of a paragraph that needs breaking is classified once (`Builder::classify`: its tier and the x it must fit by, from one forward pass of UAX #14 and of `be_lib_graphemes::grapheme_boundaries`), and breaking is one pass forward per line plus at most a zone past it, so laying out a paragraph is linear in its length. Each line records the range of widths that break it the same way (its `reach` and `limit`, which account for the zone moving with the width), so a resized `Text` reuses its layout while no line would change, and an edit resumes from the line before it.

`measure_text(node)` answers index-to-point and point-to-index from the node's last layout. Inside a `Drawing`, `painter.lay_out_text` returns a `TextBlock` that `painter.draw_text` draws, so what is measured is what is drawn; the same `TextBlock` comes from `lay_out_text` outside one.

## Layout scale and raster

Two scales, like pinch-zoom and Ctrl+/- in a browser:

- **Layout scale** (`Context::pixels_per_point`, platform scale times zoom): text is laid out and everything snaps to the pixel grid at this scale, and galleys are cached by it. Changing it lays the document out again.
- **Raster** (`PainterState::raster`): how much finer a subtree is drawn (a hosted window's scale, a zoomed canvas's `Zoom::raster`). Only painting reads it: under a raster other than 1, FreeType rasterises glyphs unhinted at the scaled size at their laid-out positions, so a zoomed canvas is sharp without relayout. The browser's backend ignores it.

## Styled text

`styled::Text`, `Span` and `Icon` take the base children and resolve tokens into a font and colour: `size` (a `TextSize`), `weight`, `family`, `italic`, `color` (a `TextColor` role resolved through the theme, `Custom` only for colours that are data), `style` (a `TextStyle` preset whose props a given prop overrides) and `overflow`. Text wraps by default, so a one-line label in a button, row or bar takes `overflow=Overflow::Ellipsis`. `TITLE` and `HEADING` are accessibility headings on both cores.

An icon beside a label is one `Text`, not a row of two; the icon sizes itself from the text:

```rust
view! {
    <Text style=TextStyle::CAPTION>
        <Icon glyph=ICON_CLOCK />
        "Edited five minutes ago"
    </Text>
}
```

`TextStyleProvider` is context, so it reaches what is *created* inside it, which is not always what is laid out there: text a render callback builds for an overlay takes the provider around where the callback was written. A `Span` or `Icon` inside a `Text` takes what it does not set from that `Text`. Raw pixel sizes and `Color32`s are for base `Text` drawn rather than designed (canvas labels, a terminal, a game board).

## Fonts and icons

`crates/beui-fonts` holds the faces (Inter, Hack for monospace, Noto Emoji as fallback, Lucide for icons): their bytes, which beui-font-freetype loads, and `FACES`, from which the HTML core writes `@font-face` rules. Its BUCK exports each file for web bundles.

Icons are Lucide's, in `crates/beui-lucide` (re-exported as `beui_core::icons`; it knows nothing of beui, so the block catalog uses it too). An icon is a `Glyph` that only the list can make, so an icon prop cannot be handed text. Anything saved holds an icon by name, since Lucide renumbers codepoints ([decision](../../decisions/beui_icons_are_saved_by_name.md)). To find an icon for a purpose, search the tags in `crates/beui-lucide/src/list.rs` ("duplicate" finds `ICON_COPY_PLUS`) rather than guessing from names. The list is generated; to update Lucide, unpack the package (`npm pack lucide-static@VERSION`, `tar xzf`) and run `./scripts/buck run //crates/be-tool-local:bin -- icons PACKAGE` from inside the repository.

## Text areas

`unstyled::TextArea` is the multiline editor, built from ordinary nodes: a row per document line in a `VirtualList`, each a `Text` of the line's spans, with a gutter and list markers, voids and embedded widgets as `TextItem`s. It owns a `beui_text_editor_core::Core` through a `TextAreaState` the caller holds. Inline and block `TextWidget`s the caller names are how a block editor embeds a block in the text and drives the document from its own toolbar.

- Nothing polls the document: code that changes it from behind (adopting a remote edit) calls `TextAreaState::sync()`; `end_undo_group()` also ends the undo group, which blur and submit do, and which a document whose own history cannot span an outside edit needs (a host-grouped `LiveText` must not: a peer's edit would cut its steps).
- `TextInput` is the area's single-line mode over a buffer it owns, so a fix to editing lands in both (except the HTML core's plain `<input>`, [components.md](components.md#inputs-and-forms)).
- `read_only` keeps the area focusable and selectable but refuses every edit; `disabled` removes it from focus and input; `find=false` lets Ctrl+F reach the surrounding program.
- Text is measured only from the tree: the area reports its size through `on_content_size`, and a caller sizes a box from that (the canvas grows a text entity while it is edited). It takes its view size from its own layout, so one inside a scaled `CanvasItem` is not laid out again on pan or zoom. The one layout away from the tree is the canvas's export, `TextAreaState::lay_out_prose`, which hands lines to a layout function the caller passes so the area names no core.
- A focused area whose view gets shorter (a phone's keyboard or a bar coming up under it) scrolls a caret that was in sight back into sight, so the row holding the caret stays built and the input method keeps being told the caret's rectangle rather than the whole area's. A caret already scrolled away stays where it is.
- `styled::TextArea` takes tokens (`size`, `color`, `padding`) and has no scale prop: text drawn zoomed sits in a scaled space.
- `line_numbers` (reactive) shows the gutter of line numbers and folding arrows beside a document that is not rich text. It is four digits wide whatever the line count, so the text never moves as lines are added; a longer number shows its last four digits. A markdown document sits in a centered column either way; beside the gutter its markers do not hang into a margin of their own. The text app keeps it off until it is chosen from its frame menu, a choice of the view kept in its view state (`LineNumbers`), not in the text.
- `scroll_past_end` leaves all but a line of the view as room below the last line, so it scrolls up to the top, as `editor.scrollBeyondLastLine` does in VS Code. Only an area that fills a place of its own takes it (the text app's): one whose height follows its text would grow with the room.
- Where the view is scrolled to is a place in the text, not a pixel offset: `TextAreaState::scrolled()` publishes a `ScrollAnchor` (the byte the top line starts at, and how far into that line the view begins) as the view moves, and `scroll_to(anchor)` puts that line back at the top: it moves to the line's estimated place and stays pending, trying again when the scroll or the laid-out rows change, until the line's row is built (its place is then exact) or the text is too short to scroll that far. A rewrap at another width keeps the same line at the top. `scrolled()` holds still while a `scroll_to` is on its way. The text app keeps one in its view state with the caret, each place as its byte and the text on either side of it, since a text is stored as its bytes and every load numbers it anew: a reopened text finds each place by that text nearest its old byte, so it follows edits made while it was closed (crates/be-app-text/src/root/position.rs).
- Up and Down move by the rows the view shows, not by source line, so a wrapped line is crossed a row at a time. The core asks the view through `VisualRows` (`beui-text-editor-core/src/core/rows.rs`), which `CursorHorizontalPositionMetric::Screen` carries: where across its row a caret sits, and the row before or after it with the caret stop nearest a goal x the core keeps across repeated moves. The view decides what a row is (a wrapped row here; a hex view's fixed-width chunk would do too), skips rows it hides, and flags a row whose end is the next row's start so the caret settles a stop before it. The area answers from its laid-out rows (`Surface::row_step`) through the `TextAreaLayout` it publishes, and `TextAreaState::move_by_row` is the call; a caret whose row or neighbour is not built (far from the viewport) moves by source line instead, as `Byte` does. Home and End still go by source line; Ctrl+Home and Ctrl+End go to the document's ends, as Cmd+Up and Cmd+Down do on Apple's systems (guides/beui_keyboard.md).

### Looks

How the area draws is three render hooks keyed by the line description (`LineLook`) markdown and rich text both give, as in Slate: `leaf` turns a styled run into a `Span` (so every run stays in the line's one `Text`), `marker` draws a list marker or void inside a `TextItem`, and `line` wraps a line (quote bars, code block backgrounds, indent). They come in a required `TextAreaLook` with `TextAreaColors` and the `TextAreaGeometry` of every absolute size; unstyled keeps only proportions of the text size. `styled::text_area_look()` and its siblings build them for a theme, and a caller drawing voids handles `MarkerKind::Void` and passes every other marker to `DocumentMarker`.

The engine says what is on a line, never how big: markers are measured by their `Text` during layout, and wrapped lines hang after them. A marker's piece is keyed by its kind (bullet, written bullet, number, check, void), so a line whose marker changes kind (a bullet edited into a task, by a person or a peer) gets its hook built anew, and a `marker` hook chooses what to draw from `kind` once, untracked; what a kind carries (its number, whether it is checked) it follows reactively. In markdown and plain text whitespace is real text, and its markers are the row's `glyphs`, so selecting never moves text. A line's newline is no text of the row; its marker is drawn in a `Blank` after the line's end, as wide as the marker, so it never wraps the last word or makes a row of its own. A control character with no width of its own (NUL, BEL, CR and the rest of C0, and DEL; not tab or newline, which have widths, nor a zero-width space, which means to be none) is shown as its ASCII name in a smaller monospace font, always: the row lays the name out unseen in the character's place, so it takes the name's width, and draws the name over it as a glyph. The bundled fonts have no Control Pictures, so the names are letters.

Markdown is parsed by tree-sitter-md, which reads a last line with no newline after it as something else (`---` as a paragraph, `# a` as an error), so it is always given whole lines: a window that does not end in a newline is parsed with one added. Lines are drawn as the tree reads them: a box with nothing after it (`- [ ] `) is a bullet holding `[ ]`, as in GFM. A rule's characters are unseen: each takes an equal share of the line (a `Gap` sharing the width, less the character's own width and a little slack, so a browser measuring the character a little wider never wraps the row) so the caret steps across the drawn rule a character at a time. What follows its last character (trailing spaces, a carriage return) is laid out as on any line, its width taken from the shares (the newline's `Blank` hangs, so takes none); a rule after a marker (in a quote or a list) keeps its characters' own widths. A table row with fewer cells than the table closes after its own last cell. A table's pipes are unseen too, its grid lines drawn apart from them: each pipe is laid out right after what comes before it, and the room up to the next cell's content (or, after a closing pipe, to the outer line) follows it, so in `|a|b|` a caret before the middle pipe stands just right of `a`, one after it just left of `b`, and selecting the pipe fills the room between them, the line included. A leading pipe stands at the row's start; between the pipes of an empty cell is one place, where its content would start. The caret still stops at every byte, so the arrow keys cross a pipe a step at a time.

A fenced code block in markdown whose info string names a language with a highlighter (Rust, TOML, Zig) has its contents colored by it; `Language::for_code_block` maps the info string's first word (`rust,ignore` is Rust) and the common aliases (`rs`), and a rich text code block's language goes through it too. There are no other highlighters, and a block naming another language stays plain code.

### Rich text

A `TextLanguage::RichText` document is structured as in Slate: the bytes are the text alone, every line is a block, and formatting is a set of `Marks` beside the bytes, each setting a key over inline text or whole lines. A `Schema` (`beui-text-editor-core/src/schema.rs`; `schema::basic` has the usual marks and blocks) gives keys their meaning: what Enter, Backspace and Tab do to a block, the tools, each leaf's style. `Core` owns only generic operations (`SetMark`, `SetBlock`, `InsertVoid`, `Transform`). Copy and paste carry marks: a `TextFragment` holds each chunk's marks as byte ranges (block marks start at a line's start and give it its props) under the schema's `Schema::name`, and a paste keeps them only from a fragment of the same name, putting them in place of those the pasted text would inherit; a block mark applies only where it starts a line here too. A key whose value is a block's id (`Schema::names_block`, basic's `EMBED`) travels in the item's refs, so the host translates it. An embedded block's id is not access-checked when it is pasted; the host checks access when the embed is shown. A decoded fragment drops marks that do not fit their chunk, a paste snaps marks to whole characters, and `Schema::admits` turns away pasted values a schema refuses (basic's unsafe links). A schema that writes and reads `text/html` says so with `Schema::html`, a `SchemaHtml`, which a text area offers and takes after `be3/text-fragment`; `beui-text-editor-core/src/html.rs` tokenizes any input in one pass, and basic's reader (`schema/basic/html.rs`) keeps what maps to its marks, inline `style`s included, safe links only (http, https, mailto), and the rest as text. `styled::FormatBar` shows a schema's tools.

Marks (`be-lib-sequence/src/marks.rs`) are anchored to sequence positions and converge in any order, so copies exchanging them agree; the demo's Rich text page sends them over a simulated network. Undo removes an edit's marks rather than marking old values over them, so a concurrent mark from another copy survives.

## Selecting text

`Selectable` (`styled::SelectableText` over it) is each core's own read-only selection: the browser's on HTML, and `beui-view/src/native/selectable.rs` natively, which selects across the `Text`s under it and across `VirtualList` rows, built or not. A selection end in a list is a key, a text index and a byte index, never a node, so a recycled row cannot carry it to another key. Select All and copy work without building rows; copy reads unbuilt rows from the list's `text` prop, and a list without one copies them as empty lines. `selected_text` reads the document, so it works only from a handler or inside `with_reactive_scope`.
