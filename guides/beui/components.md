# Beui components

The unstyled and styled component layers, and the base nodes they compose. Text, text areas, fonts and icons are in [text.md](text.md); overlays, menus' layers, dialogs, toasts and trees in [overlays.md](overlays.md); writing views and the base layer's internals in [core.md](core.md).

## Layers

| Layer | Crate, public path | Owns |
| --- | --- | --- |
| Base | `crates/beui-view/src/components` (bodies in `src/native/` and `src/html/`); `beui::primitives` | Layout, painting, focus, pointer input, offset content, text, per core |
| Unstyled | `crates/beui-components-unstyled`; `beui::unstyled` | Interaction, keyboard, touch and accessibility, with no appearance |
| Styled | `crates/beui-components-styled`; `beui::styled` | Themed controls: an unstyled control plus a face painted from `styled::theme` tokens |

Work at the highest layer that can express the change. For a new look on existing behaviour, paint the unstyled component's handle: a styled control that reimplements focus, keys or pointer handling drifts from every other face of that control. New behaviour is a new unstyled component; a new base node is only for what no arrangement of nodes expresses ([decision](../../decisions/beui_base_layer_kept_small.md)).

Each crate's `lib.rs` re-exports are the list of what exists. Code outside beui reaches the unstyled components that draw nothing (`Draggable`, `DropTarget`, `Floating`, `PointerLock`) through `beui::styled`.

`TextArea`, `TextInput`, `Picture` and `Window` are compositions, the same on both cores; `Selectable` is the one component each core builds its own way ([text.md](text.md#selecting-text)).

## Base nodes: traps

[core.md](core.md) covers the base layer. What trips component code:

- `List` is the only row and column; there are no `Row`/`Column` aliases ([decision](../../decisions/beui_list_props_over_row_column_aliases.md)). A shrinking or growing child never gets less than its `Element::min_width`.
- A `Frame`'s `max` caps the room it takes, not its content (CSS `max-width` on a block): `Extent::at_most(320.0)` is 320 wide however little its content needs. A box as wide as its content up to a cap is a list child in `<ListItem max=..>`. A rotated frame takes input unturned, so `rotate` suits pictures, not controls.
- A stretching parent (`List`'s default `Align::Stretch`, `Frame`, `Grid`, `Layers`, `Offset`, `VirtualList`) stretches only a child with no size of its own on that axis, as CSS's stretch does: a `Frame` with a fraction width (`Extent::fraction(0.25)` in a column) is measured and placed at that size at the start, through `layout::stretched`. A node answers through `Element::sizes_itself`; one that lays its child out in its own rect (`Interactive`, `Portal`, `Embed`) asks its child. An exact or `max` width needs no hook, since the frame draws its box at that width at the start of its rect, but it takes input across the whole stretched rect. The HTML core gets this from CSS, and beui-tests' `stretch` holds both cores to it.
- Nothing has a hidden state while in the tree: use `Show`, with a `fallback` in a slot that always holds one child; to keep a branch's state while hidden, show a `Kept` in it, inside a `KeepAlive` around the `Show`.
- A node no `Portal` shows keeps the arena parent of the last portal that showed it, so code walking up checks each parent still lists it.

## Tokens and theme

Styled components take design tokens from `styled::tokens` (`Space`, `Padding`, `Size`, `Length`, `ColorRole`, `TextColor`, `Radius`, `Border`, `Stroke`, `Movement`; [decision](../../decisions/beui_styled_components_take_design_tokens.md)). A raw number in a styled prop does not compile, and the source lint rejects `Extent::px` outside beui's crates. `Custom` variants are for values from content (a user's tag colour, a canvas). Each token has one value, and `.px()` gives the pixels an unstyled prop takes. Density (`provide_density`, `use_density()`; a phone frame provides `Density::Comfortable`) sizes the tree alone: the styled `Tree` and be-app-file-tree's rows read it and own their comfortable metrics; nothing else changes with it. Converting pixels, snap to whichever neighbouring step looks right.

Containers use two fills: `Background` for what everything sits on, and `Surface` for every panel above it, floating ones included (bars, popovers, menus, tooltips, dialogs, toasts). A floating panel stands apart from what it covers by its `Border::DEFAULT`, not by a third fill. `Control` fills what you press, type into or drag (fields, unchecked boxes, chips, tiles, keys, cards you pick or move), so a control shows up the same way on any panel. `Shade` tints an area inside a panel that is not a control: code, a header strip, a highlighted lane.

Colours on primitives are `beui::Color`: a literal, or a reference to a `ColorVar` (`beui::color_var!`) that whoever uses it defines per scheme with `define_colors`. The HTML core writes references as CSS variables with light and dark definitions, so a prerendered page shows the browser's scheme before any script runs. Code that picks a colour by reading the theme kind or scheme renders a prerendered page wrong, since server and browser can disagree; pick a reference whose definitions differ per scheme ([decision](../../decisions/beui_colours_are_scheme_references.md)), and call `resolve_color` only where a `Color32` is needed (a `Drawing`).

`styled::Theme` (`theme.rs`) is the one place theme colours live. Read it with `use_theme()`, one signal per token, so a component wakes only for colours it uses. `ThemeProvider` gives a subtree literal colours; `define_themed_colors` and `theme.themed(..)` give a caller's own per-theme colours the same scheme treatment.

## Controls

- **Buttons.** `unstyled::Button` owns semantics, activation, disabled state and accessibility, and hands its face a `ButtonHandle`; a button that opens something is a `PopupTrigger`. A read-only editor binds `disabled` to `editor.read_only()` rather than leaving a live control that drops edits. Icon-only buttons need no tooltip wrapper: `icon_only` turns the label into the tooltip.
- **Rows and tiles.** `RowFace` is the one pressable-row look (list, action, settings, menu-sheet and palette rows); `TileButton` picks among pictures, `SwatchButton` among colours. `ToolPill` is the bar floating tools sit in. `keep_clear(node, rects)` names parts of a node something floats over, so revealing focused content avoids them.
- **Anchored popups.** Callers never choose dropdown or sheet: `unstyled::Anchored` opens a dropdown for a mouse and a `ModalSheet` for a finger ([decision](../../decisions/beui_anchored_popups_sheet_on_finger_touch.md)). Menus, `Select`, `Popover`, `Tooltip` and the pickers sit on it; every component with a menu takes a required `MenuStyle` for both looks. Every popup (`Popover`, `MenuButton`, `ContextMenu`, `MenuPopup`, `Select`, `Tooltip`) takes the same props for being open and placed: `open: Binding<bool>`, which its own trigger, keys and dismissals write as an owner may; `at: Binding<Option<Pos2>>`, a window point it opens at instead (pinned to its anchor's node, as a context menu opens at the press); `placement`, any core `Placement`, its gap and margin included; `bounds`; and `keep_alive`, which keeps its content with its state while closed (on by default only for `Popover`). A `Popover` without a `trigger` is no button: it hangs from the `anchor` it is given and opens only through `open` (an editor's child popovers, be-sdk-beui's `popover.rs`); its `beak` (`arrow` on the styled one) points from the frame its surface binds to `Dropdown::pointer`. Focus goes back through the layer's focus scope (overlays.md, Focus and layers), never a popup's own refocusing. `MenuNodes` builds rows from a description of actions (guides/beui_keyboard.md, Actions and the command palette), so one description fills every menu. Popup content focuses by binding `focused` to the handle's `shown`, not to `open`. A `Select`'s list opens `BELOW_START` like any popup unless given `Placement::Menu`, and is at least as wide as its trigger (`Dropdown::anchor_width`, the anchor's measured width, a frame late on the HTML core); in a dock pane, pass the pane's measured rect as `bounds` so the list keeps off the dock's bands (beui-demo's Dock bars page, `LayersSide`). A `Tooltip` shows after `TOOLTIP_DELAY` of hover, or at once while its child holds the keyboard's focus (`focus_ring(holds_focus(..))`); every tooltip in a document shares one warm-up, so while one is shown, or for `TOOLTIP_COOL_DOWN` after the last closed (read from the frame clock when the next is hovered), the next opens without its delay. Its label describes the first node within its child that has accessibility of its own (`bind_description`; `aria-description` on the HTML core) unless that node has a description already or the label is its name, as an icon-only button's is. The styled `Tooltip` stands off its child by its placement's gap (`TOOLTIP_PLACEMENT`), so a caller's own placement carries its own gap. `Anchored` with `sheet` fixed at `SheetWhen::Never` returns its overlay alone, with no list around it and no `Show` for a sheet. A menu row's submenu opens once the pointer stays on the row for `SUBMENU_DELAY` and gives way to another row after the same delay, or after `SUBMENU_GRACE` while the pointer heads for it: each move inside the triangle from where the pointer was to the submenu's near edge (`menu.rs`, `heading_into`), so a diagonal path across other rows keeps it open (not across windows: a submenu escaped into another window has no coordinates in common with its row). A click or a key acts at once. Rows hear the pointer through `Button`'s `on_hover_move`, gated on `pointed`. Tests let the delays pass with `pause`.
- **Choices.** `Choice`, `Select`, `RadioGroup`, `Tabs` and `SegmentedControl` bind the chosen option's value, never its position: each `<ChoiceOption value=.. label=.. />` names what it stands for (an id, a key, an enum), and `selected` is a `Binding<Option<T>>` (`Binding<T>`, `#[prop(required)]`, for tabs and segments, which always have one). A value no option holds shows nothing chosen, so a list that changes between a frame and a click never picks whatever moved into a position. `posted` is what a `Form` posts, the label without one. An option's `value=` is a plain `T` fixed when it is built, unlike control flow's reactive `value=`; an option whose value changes is a new option, keyed by that value in its `ForEach`.
- **Sheets** scroll their own content; a vertical `Scroll` inside one measures nothing tall.
- **Dates and colours.** `beui::datetime` values carry no zone (`DateTime::from_unix` reads UTC seconds, as block content stores). Value controls write `value` on every move of a drag and report the drag around those writes as `ValueDrag` (`value_drag.rs`): `NumberInput` through `on_scrub`, `Slider`, `ColorArea`, `ColorWheel` and the colour pickers and inputs through `on_drag_change`. `Started` comes before the first write, a press's jump included; a cancelled drag writes back its start before `Cancelled`; a control disposed mid-drag reports `Cancelled` (`DragReport`, which a new value control uses too). An owner writing block content holds the writes in a tentative gesture (guides/adding_an_app.md, Gestures); one that cannot wraps its value in `HeldValue`, which shows the drag and writes once when it is kept. These drags and a scrollbar's stay on `on_drag` until they move onto the drag board (Drags as places, below; plans/declarative_dragging.md, step 8), which can now lift at a press, carry without scrolling and carry one item per pointer; a dock splitter already has (guides/beui/docking.md, Dragging). `SliderScale::Midpoint` curves a slider ([decision](../../decisions/beui_slider_midpoint_exponential_curve.md)).
- **Treemaps.** `Treemap` shows one level of sized items as squarified tiles (an area per size) and goes into a tile that `opens`; the caller holds the `path` and derives `items` from it, so a level is listed only once it is gone into, and a tile's size is the item's own data, never a sum of what is below. A level past `TREEMAP_MOST_TILES` shows the largest and one tile for the rest, so it lays out in time linear in its items.
- `component_placed()` tells a component whether it is laid out, so work like a progress sweep stops while hidden.

## Scrolling

Program code wants `styled::Scroll`, which adds the overlay scrollbar ([decision](../../decisions/beui_overlay_scrollbars.md)) and edge fades. `unstyled::Scroll` owns input and momentum and takes a `ScrollStyle`: the spring overscroll comes back on (`ScrollStyle::new`), the bar, the edge fade and the marker a middle-button autoscroll shows where it started. A control that scrolls something of its own takes one and passes it down (as `Select` and `TextArea` do), so `styled::scroll_style()` gives it the whole look. Under both is the base `Offset`, which answers no input and never clamps.

- Padding goes inside a scroll because a focus ring needs room at the content's edges; a scroll that is part of a padded surface takes `bleed` instead.
- Content is laid out at least as long as the scroll, and content that overflows is first shrunk to `Element::least_length` (shrinking children give up length), like a flex box in `overflow: auto`. A scroll sized to its content up to a bound is `max_length`; a `Frame` with a `max` around it fills up to the max instead.
- Scrolls chain as in a browser: one at its edge when a gesture starts turns it down, so the enclosing one takes it. A horizontal scroll leaves a plain wheel to what is around it.
- The offset is anchored to the node at the viewport's top, so content above it changing size leaves what is read in place. `follow_end` keeps a log or terminal at its end while it grows.
- On the HTML core `unstyled::Scroll` is a real `overflow: auto` element through the platform escape (`BrowserScroll` in `scroll.rs`): the browser scrolls and chains it, with none of beui's momentum, rubber band or drawn bar.

### Long lists

Layout culls nodes more than `CULLING_MARGIN` outside the view (never the focused node, nor anything holding an open overlay), so a long scroll of ordinary content needs nothing more. A `VirtualList` is for when building every row is itself the cost.

It can sit anywhere a tall child could. Its trap is recycling: the row builder runs once per built row with a `ReadSignal` of its key, which the list later points at another key. Derive everything shown from that signal; state a row keeps carries over to the next key, unless its content is in `<Dynamic value={key}>`.

Rows measured anew (an estimate replaced, content that grew) move what is beyond the row the list keeps in place: the first row it builds, which with `overscan` is above the view. A list that knows which row the reader is at names it with `anchor` (a text names the line at the top of its view), and the rows around that one move instead. The scroll reports its position only from a layout whose offset and rows agree: one that shifted the offset to keep the anchor reports from the layout after it.

## Inputs and forms

On the HTML core a plain single-line `TextInput` is a real `<input>`, so the browser gives it IME, autofill and password managers; every other text field is beui's own on both cores ([decision](../../decisions/beui_html_text_input_is_a_native_input.md)). A new kind of single-line field is an `InputKind` variant. `Form` is a `<form method="post">` on HTML, so a server-rendered page posts before wasm loads; natively it is no node. Fields beui draws itself (`Checkbox`, `Switch`, `Select`, a beui-drawn `TextInput`) post under their `name` through a hidden input: a checked box `on`, an unchecked one nothing, a `Select` its option's `value` (its label without one), and a disabled field nothing, as in HTML.

The platform escape, `beui::escape::html_escape`, puts a browser element into the tree. It panics natively, so it goes under `if CORE == Core::Html` in unstyled or styled, with a beui version in the other branch behind the same API. It is only for components whose HTML form is the browser's own element (a field, form, link or scroller), not for working around a primitive a core lacks ([decision](../../decisions/beui_platform_escape_only_for_browser_elements.md)).

- **Files.** `create_file_picker(picked)`: nothing blocks; the runner hands the request to `Platform::pick_file`, and the answer arrives in a later frame's reactive scope.
- **Pointer lock.** `unstyled::PointerLock` asks for the pointer through `WindowRequests::pointer_locked`; whoever shows the document locks it, and motion arrives as `Event::PointerMotion` to the focused node only. A browser drops a lock on blur and Escape itself and refuses one without a user gesture; the document answers by clearing focus.
- **Pan and zoom.** `unstyled::PanZoom` turns gestures into a caller-owned `Binding<PanZoomView>`; momentum, snapping and clamping to content are the caller's (guides/pan_and_zoom.md).

## Drag and drop

Within a document: `Draggable` on what moves, `DropTarget` on where it lands, meeting on `unstyled::drag_board()`, one `Board` per document; nothing else wires them. Of the accepting targets under the pointer the one painted last wins, so nested slots each take their own drops. The board is written once, in unstyled `drag_board.rs`: each core only says where its nodes are (`beui_view::drag::space()`, a `Space`) and drives it (`drive`, a `Driver`): natively from the pointer each frame, across windows, and with Escape; on HTML from window listeners while a drag is carried, so it goes on after the element that began it is gone. Change drag behaviour there, and test it with its fake `Space` (`drag_board/tests`). The board also floats the item (a source's `floating`, unless the target under it `hides_preview`), tells every target the drag ended before the taker's `dropped`, and scrolls the innermost `Scroll` whose edge band (`EDGE_BAND`) holds the pointer. A finger drag on a `Draggable` in a scrolling list needs `touch_drags`, or the list scrolls. A drag between editors crosses apps and goes through the host (`Editor::drag`, guides/apps/host_services.md), which carries it on its own board with each app region a `DropTarget`.

### Drags as places (replacing the above, plans/declarative_dragging.md)

An `Interactive` given `drag` lifts a `Carry` at the first drag of a press past the drag threshold, with `lifts_on_press` at a mouse's or pen's press (a thumb or splitter that follows the pointer from its first point; a finger still lifts past the threshold, which tells its drag from a scroll, and a press that lifts and never moves still clicks), or, with `lifts_on_long_press`, at a finger's long press (`None` lets the press go on as `on_drag`, or `on_long_press_drag`, hearing first the moves it made short of the threshold, which are held until then, or, for a press that never reaches it, as it ends, after its click and before `on_active_change(false)` (a called-off press hears none), so a stroke keeps its first points); a held finger is otherwise a secondary press, the way to a menu, so leave it off for a source with one; from then the board follows the pointer that lifted it and the press hears no more drags. Each `use_drop_site(accepts, spec, commit)` that accepts the payload gives its places as a `DragSpec` (`closest(slots_in(..)).when_far(floating())`, read from the layout at the lift); every point chooses the closest place of them all, a place always before floating, and tells only the site whose choice changed through its handle's `over`. Only places in the window the point names count (each node's window comes from the core as it tracks the carry), unless the carry is `kept_in(window)`, which reads a point over another window in that one's points where they relate (`window_point`; a dock's tool bar, drawn above its dock's own windows) and as over no place where they do not; and while a `when_held(modifiers, held)` holds its modifiers, its `held` places are the only ones of any site (a dock's Alt floating its tab over every bar). A `when_far(far)` takes `far` whenever its near side chooses no place (all of it closed by `open_where`), however near. A `thrown()` spec carries a release faster than `THROW_SPEED` on along its path for `THROW_SECONDS` before it chooses; `thrown_for(seconds)` changes how far and `with_distance(speed)` how fast (a sheet throws every release, `with_distance(0.0)`, for 0.2 seconds, choosing among its detents with `evaluate` where its own continuous drag lets go, with no carry). A `custom` place is asked about every point wherever the pointer is: its `place` answers `None` where its node does not take the item. A zoned candidate given `nearest_edge(edge, rect)` is chosen in its zone only where the pointer is nearer that edge of `rect` than any other, in proportion to its size (a pane's edge bands, splitting each corner along its diagonal). `open_where(open)` keeps a spec's places to points `open` lets through, floating elsewhere (the dock's places are reached only where none of its other windows or dialogs, nor anything else, covers them), and `shaped(within)` draws the item the size of the place chosen, still under the pointer at the fraction of it where it was grabbed but kept inside `within` (a dock's tab drawn as the pane it would open, inside its surface). `free(area, drop)` keeps the item inside `area`; `.unbounded()` lets it go past the edges (a canvas, whose area is a window onto its world). A release commits the chosen place to its site before the site hears it is over nothing, so a site that previews by writing tells a drop from a put-down (it writes from its own effect on `over`, at once: the board hears pointer points in `end_frame` after the `after_input` hooks, so a write queued for after input reaches layout a frame late); Escape, the lifting pointer's cancel, a site going or the source's node going commits nothing, and a release outside every window on no place tells the carry's `outside`. A carry the core does not track (a dock bar an app's grip carries across the app protocol) is lifted by `PointerId::Relayed` and moved and let go with `Driver::track` and `Driver::release` by whoever relays it. The board holds one carry per pointer (the mouse, each finger, each controller, the keyboard): a pointer that carries lifts nothing more, a source already carried is not lifted again, each pointer's points move and release only its own carry, and Escape puts down every one. A site gives places to one carry at a time: a second carry lifted while it gives them to another gets none from it, and none later either, even once the first ends, since places are read at the lift. A component names its own carry by its payload's value, so two carries of one type (rows of two lists with one key type, two splitters) stay apart: `Board::carries(&payload)` and `Board::frame_of(&payload)`; `carrying::<P>()` lists every carried `P` and `is_carried(key)` asks whether any carry holds it. Whether the pointer is outside every window is one flag for the board (`Driver::set_outside`), not one per pointer. (The native core turns a second finger in a window into a gesture and cancels the first finger's press, so two fingers do not carry at once there; the mouse and a finger, or two controllers, do.) While carried, the item scrolls the edge scroller whose band holds it (`Board::register_scroller`, along either axis or both: a `Scroll`, or a canvas panning its camera), unless the carry `scrolls_nothing` (a value's thumb, whose form must not scroll under it); of several carries, the first in a band scrolls it until it leaves; and `Board::retrack` chooses again where the pointer still is once what is under it has moved. While it floats the item is drawn as the source itself, displaced and raised above its siblings but still clipped by a scroll around it; a carry that must leave its scroll (a kanban card moving between columns) gives `Carry::preview`, which floats in a top layer instead, and one a site draws itself gives `Carry::drawn_by_site`, so the source draws nothing for it (a `CarryFace`). A source carries from the keyboard while the focus is on it (`focusable`) or on a node within it (a dock tab's row, whose tab button holds the focus; guides/beui_keyboard.md has the keys): Ctrl+Shift and an arrow move it one place, Move in the palette or (on a source that does not activate, unless `lifts_on_space=false` keeps Space for another, a canvas's pan) Space lifts it, the arrows step it to the nearest place that way (`step_toward` over the spec's fixed places, aiming at a place's zone when it has one, a step across counting twice one along, and a `nearest_edge` place answering only the arrow its edge faces), or, with no fixed place that way and a `free` one to move in, its step that way (`FREE_STEP` points unless it is `stepped`; ten steps with Shift), Space or Enter drops it, and Escape or Tab puts it down without moving focus (while the keyboard holds it these keys reach it before the node within it that has the focus); a live region on the source says the lift, each place (`Candidate::labelled` names it) and the end. A carry's tracked frame (`frame_of`) is in this window's points; outside every window it chooses no place (a release there tells its `outside`) unless it `reads_outside`, which reads its places at the captured pointer still (a splitter clamped past the window's edge); a site shows a carry to peers by publishing its `over` as presence in its own terms (a canvas the offset of the selection it carries), which their copy of the site draws. Specs are pure (`evaluate`, tested without a core in `beui-types`); the board's carry is in unstyled `drag_board/sites.rs`, tested on its fake `Space` (`drop_site/tests`).

### Reorderable lists

`Reorder` (the unstyled one takes the `spring` its rows and gaps settle on; the styled one settles on `Movement::Settle`, and its `ReorderItem` adds a lifted look) makes a container's items draggable into a new order. It is a drop site whose rows are drag sources (Drags as places, above): render `ReorderHandle::order`, not your keys, in a `ForEach` or `VirtualList` handed `ReorderHandle::rows` as its `handle` (how the `Reorder` finds its rows, and `slots_in` their places), and make each item a `ReorderItem` that is the container's own child, since its root is a `Glide`. `Reorder` glides the moves it makes (a carry to another place, a drop, an Alt+arrow step): each row it moves, or that its open gap passes, glides from where it was. A list whose order changes for any other reason (an insert, a sort, an edit elsewhere) does not animate, as no list does. A lifted row is shown on the place chosen and follows the pointer along the list (`DragSpec::following`, which chooses by distance along the line), passing a neighbour once its leading edge crosses that neighbour's middle (the list's spacing is its stickiness). Carried off the list it collapses (a `collapsed` frame, taking no space or spacing) and the slot it leaves closes on the spring; carried off by the keyboard it keeps the focus instead, so it is drawn at no size and opacity 0 rather than collapsed (which blurs it on HTML and leaves it unplaced natively), keeping its spacing, and its slot closes the same way, opening again for it if it is let go where nothing takes it; it floats as the `preview`, which the `Reorder` draws at its own root, since a collapsed row draws nothing (the row's carry is `drawn_by_site`); another `Reorder` that `accepts` the payload opens a gap where it would land and draws the `preview` in it. A row no other site takes never floats: however far it is carried it stays on its own list's places. A finger lifts a row by dragging it across the list, or, with `lifts_on_long_press`, by holding it (for a list whose rows have no long-press menu). `on_move` hears one `ReorderMove { payload, key, after, index }` per drop or Alt+arrow (`step`), from the list it lands in, which makes the move (decisions/beui_a_move_between_drop_sites_is_the_apps.md); apply it synchronously, or the item glides back. `fixed` (with `slot`) is for an order decided elsewhere, a sort: a carry from elsewhere has one place, where `slot` sorts it, and the list's own row floats at once with its slot kept open. `hover` parts the list for a drag the board does not carry, as `styled::Tree`'s `reorder` does. `on_outside` hears a row let go outside every window (where a host opens windows); the dock's tab bars are `Reorder`s and float such a tab into a window of its own.

## Touch and pen

A finger held still is a secondary press (tests set `Context::set_long_press_delay` to zero), and the press it began is cancelled (`on_cancel`). A finger drag across an `Interactive` scrolls whatever around it scrolls that way unless the catcher sets `touch_drags`. A finger landing on no control goes to the nearest within `TOUCH_REACH`; a catcher that only watches a region sets `claims_touch=false` so it does not take that reach. The pen behaves as the mouse.

## Time

beui has no per-frame hook. Anything time-based uses `create_timer(work)` (work returns the next delay or `None`) or `create_animation(step, finish)`, both owned by the creating scope, and nothing is drawn while none is due. A timer started during a frame and already due (a zero delay) fires in that frame once it is laid out, and the frame lays out what it changed; a timer fires at most once a frame, so one that restarts itself at zero runs once each frame. A driven program settles only when no frame asks for another (guides/running/drive.md), so motion that never ends (an indeterminate bar, a blink) ticks from a timer with a frame-length delay rather than an animation, or `drive settle` waits forever. `tween`, `Spring` and `Fling` are the curves. A curve is appearance: unstyled components take each as a required value (a `Spring`, an `Easing`, or a bundle of them such as `SheetCurves`, `SlideCurves`, `DockCurves` and `ScrollStyle::new`'s overscroll spring), while durations stay defaults. Styled code names what a motion is for with `styled::Movement` (`Settle`: landing where layout puts it; `Enter`, `Leave`: arriving and going; `Rubber`: content pulled past its end; `Pull`: a window or sheet pulled past its rest), whose `.easing()` and `.spring()` are the curve in each form; styled components pass the token their motion is for and take no curve prop. Add a movement only when a component needs one none of these names. `Glide` animates a move between layouts: whatever its `on` follows (a `Trigger` notified in the same update that reorders the keys, a signal) changes, or it is handed `from` (a window point to settle from), and its spring takes its child from where it was to where it rests. The styled `Glide` settles on `Movement::Settle`; the unstyled one takes its `spring`. It is two base `Frame`s: the outer is measured where layout puts it, the inner is drawn at the spring's offset by `translate`, so each frame lays out only the inner frame. Its `GlideApi` holds the child at a point (`hold`) and reads the offset (`displacement`); `raised` (a `Frame` prop) paints a list child above its siblings. It hears of a move through `measure`; on HTML that is read in the frame's layout pass, after the change reached the page and before the browser paints, so the child never shows in its new place first. A scroll around it is no move (`measure::scrolled_by`, on both cores), and a glide inside another (`within`) moves only against that glide's drawn child. Under `Motion::Instant` animations complete at once and inertia is off, while functional timers still run.

## Preferences

`Preferences` (theme, motion, canvas touch; `crates/be-lib-ui-preferences`, shared with the app protocol) resolve from three layers, top down: `Developer` (the inspector), `Program`, `System` (the platform's, or the host's for an app). Components read `use_preferences()` and write a layer with `use_preference_layer(source)`; `RunOptions::saving_preferences(name)` saves a program's layer, and be-host keeps them in its display settings.

## Drawing with the gpu

A viewport no arrangement of nodes can make (a 3D scene, a map) is a `Drawing` painting `draw_gpu(drawing)`; its `Draw` runs in paint order with `prepare` (device, queue, encoder) and `paint` (beui's own render pass). `be_app_scene_3d` is the worked example, and `beui::native::texture_quad` shows a texture with no pipeline of your own. Traps:

- Key shared gpu resources by `DrawAt::renderer`: devices of two wgpu instances can compare equal.
- Leave the pass's viewport and scissor as found; beui keeps painting into it.
- Drawings compare by `Rc`, so a new one each frame keeps an idle editor repainting. Build resources on the first `prepare`, so headless tests never open a device.
- A crate under beui depends on beui-draw behind a feature beui turns on outside the HTML core (beui-components-styled's `gpu`).

## Writing an unstyled component

An unstyled component has no appearance defaults: colours, sizes, spacing, fonts and renderers for anything it must draw are required props the styled layer fills ([decision](../../decisions/beui_unstyled_layer_has_no_appearance_defaults.md)). Defaults that draw nothing and behaviour defaults (thresholds, zoom limits, delays) stay.

Put it in `crates/beui-components-unstyled/src/<name>.rs`, re-export it from `lib.rs`, and usually: user-changed state as a `Binding<T>` prop with no copy kept in sync (see `Toggle`); one focusable `Interactive`; the role and state through `component_accessibility`; a `Render<Handle, NodeId>` or `RenderFn<Handle, NodeId>` of reactive state for the face; and return the root base node directly.

- **Handles.** State callers or tests read is a `Copy` type (`SelectApi`) in an `api: ComponentRef<..>` prop filled with `api.fill(..)`; a test with only a `NodeId` reads `document.api::<SelectApi>(node)`.
- **Reaching the tree.** These crates do not name `Document`, `with_document` or `NodeOf` outside tests, so they build on any core; `be-tool-fix-rust-source` reports it. Use `beui::reactive` (`beui-view/src/nodes.rs`): `TreeNode` methods on `NodeId`, `measure`, `measure_text`, `focused_node`, `tree_local` and the rest. Add what is missing there.

### Pointer input

Where a catcher hears the pointer is declared ahead of time as `Area` memos (`hit_area`, `capture_presses`, `claims`; [decision](../../decisions/beui_hit_areas_are_declared.md)). A down is hit tested once (`interact::hit`); the press climbs from the topmost catcher to the first whose `capture_presses` holds it, arming each on the way, unless a modifier claim takes it first. A settled finger drag goes to a catcher holding that axis with `touch_drags`, else the first `on_pointer` answering `true`; the rest hear `on_cancel`. Input every catcher turns down is offered again with `unclaimed` set, which is how an outermost scroll still rubber-bands. Lists whose highlight follows the pointer use `pointed`, not `hovered`, so keys can walk under a resting pointer. A view that appears under a pointer that has not moved hears it as `PointerRested`: what is under it is `hovered`, but nothing is `pointed` until the pointer moves, whichever order the view and the rest arrive in (a menu opened under the pointer that pressed its button highlights nothing until the mouse moves). Only a host sends a rest, so a `BeuiTest` cannot reproduce one.

Gestures live in `unstyled::gestures` (`scroll_wheel`, `scroll_drag`, `autoscroll`, `secondary_drag`, `pan_zoom`, `first_of`), not in the core. A part drawn outside its catcher (a text area's touch handles) claims `Area::CaretHandles` and is painted from a later node, since paint order is tree order.

## Writing a styled component

Put it in `crates/beui-components-styled/src/<name>.rs` and re-export it. It wraps the unstyled control, passes `label` on, and paints the handle with base primitives; `checkbox.rs` is a short complete pair:

```rust
#[component]
pub fn Checkbox(label: Prop<String>, checked: Binding<bool>) -> NodeId {
    view! {
        <Toggle checked label>|handle: ToggleHandle|
            <CheckboxFace handle />
        </Toggle>
    }
}
```

The face derives colours from memos over the handle's state and theme tokens, so it repaints when either changes. A focusable face draws its keyboard ring with `Frame focus={handle.focused}` (and `focus_offset` to sit outside the edge), never with a border; `beui_view::reactive::focus_outline()` stays for the base layer, which takes concrete colours. Write private consts as tokens. Add a field to `Theme`, with a value in every built-in theme, when a colour belongs to the theme rather than one component. Icons are `beui::icons` glyphs in a `styled::Icon` inside a `styled::Text`. Expected keyboard behaviour for each control family is in [../beui_keyboard.md](../beui_keyboard.md).
