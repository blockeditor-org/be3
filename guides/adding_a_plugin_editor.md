Every editor in the app is a plugin, and so is the app's own window: block-app signs the user in, switches organizations, hosts plugins, owns the app menu - which opens under the button when a plugin calls EditorHost::show_app_menu with that button's node_anchor, as the account button in the files toolbar (and the files page's header on a phone) does, as a dropdown after a click and a sheet after a tap - and owns the dialogs a plugin cannot draw for itself. Everything else on the screen - the dock of tabs, the pane of files, the menu each block's tab adds to - is crates/editors/workspace-ui, an ordinary plugin the app opens on the client's session, a view block under the account's settings block (guides/the_new_block_stack.md, Settings, settings profiles and sessions), and draws filling the window. It places the file tree and the block each tab is showing as children of its own, each owning a frame of its own (see below), so every editor on the screen is a plugin instance the app is only compositing. Narrower than NARROW_WIDTH the dock stacks itself (DockMode::Stacked, which the workspace reads from DockingLayout::mode() to know it is on a phone), so it shows one screen at a time, the file tree or one open block, under the dock's own stacked bar: back (which closes a block opened from the screen before it and returns there), the switcher, and the pinned actions and More button of the block on show. The same tabs stay open when the window crosses NARROW_WIDTH, and so do the editors in them. The only editor block-app has left is the placeholder for a block type no plugin claims. This is how one is added.

1. Add the block (if the block type is new)

- crates/editors/foo/types — the plugin's types crate: the content as #[derive(Model)] structs, impl Root with a fresh CONTENT_TYPE uuid, pub type FooContent = Document<Foo>, the edits an editor makes as helpers returning be_model::Edit, the be_block_types! list its type module is built from, and its tests (edits, references, merge, undo), one file each. guides/adding_a_block.md says how; crates/editors/checklist/types is the example.
- manifest.json — a block_types entry for it (below). Nothing outside the plugin learns about a new type.
- A block holds what it is, not what an editor makes of it. The image block keeps the file's bytes and a header saying what decoding them found — or why it failed — which the editor fills in through an operation the first time it draws the image. Nothing but the plugin then needs a decoder, and no other client has to decode the block to know its shape.

2. Create the plugin package

- crates/editors/foo/Cargo.toml — copy checklist's: crate-type = ["cdylib", "rlib"], deps block-editor-beui, beui (default-features = false, features = ["render"]), the plugin's types crate and uuid, and block-ui-test as a dev-dependency. block_editor_beui re-exports be_block, so the editor reaches the content traits and the first-party types still in be-block without depending on it itself. The package name is the wasm artifact stem, so a multi-word editor uses underscores (workspace_index). It also has to be a name no crate the workspace depends on already has, so the image editor's package is image_block; the display name in the manifest is what the user sees.
- crates/editors/foo/src/lib.rs — block_editor_beui::beui_plugin!("../manifest.json", { foo => app::FooApp });, which pairs each editor the manifest names with the BeuiApp that draws it. A plugin may hold several related editors (the logic plugin in crates/editors/logic-grid edits logic grids, logic games, hotbars and compiled logic): each is one BeuiApp under its own name - beui_plugin!("../manifest.json", { grid => app::LogicGridApp, hotbar => hotbar::app::HotbarApp, ... }), and two of them may edit the same block type. The framework opens each instance with the app of the editor id the host names, and refuses to start unless the apps cover exactly the editors the manifest declares. Related editors belong in one plugin rather than one each: they share a module, and the host runs one runtime for them.
- crates/editors/foo/src/app.rs — impl block_editor_beui::BeuiApp. An editor has no state struct and no connect: it is one component, BeuiApp::View, handed an Editor, a Copy handle that closures take with move (the instance keeps the OwnedEditor that owns its state and frees it when the instance closes, after the views built on it), and the type it names in beui_plugin! only carries that component and the two or three answers the host asks of the editor as a whole. View returns a <Root> (beui::styled::Root), whose clear_color is what the frame is cleared to wherever the editor paints nothing: the theme's background unless the editor names another role. Inside it the view is wrapped in <Loaded label="Loading the foo">, which keeps it hidden, with its effects waiting, until everything it reads (its content, the graph queries it watches) has arrived; so the content reads its sources inside <Loaded>, not in view around it (guides/reactive.md, Loading). What it wants of its block it takes as editor.block_content::<FooContent>(), a ContentProjection the framework pumps at the top of every frame, which follows the block's replica in its type module through Replica frames (guides/type_modules.md): it registers what the view reads as projections of the content - project, or field, ids and object for one field, one list's order or one object - and writes back through operate with the edits the content type's helpers build, which is already held behind whether the host says the block is editable, so a change to the block wakes the bindings that read what changed rather than rebuilding the view. An editor writes every change as it happens - each frame of a drag, a stroke as it grows, a value as it is typed - so peers see it through sync at once, and never holds a gesture back to write it on release: the client batches saving (at most every 750 ms) and is where batching belongs if live edits cost too much. It brackets a gesture with begin_gesture and commit_gesture so it undoes as one step (a NumberInput's on_scrub says when dragging its value starts and stops), and calls it off with cancel_gesture, which puts back what the gesture wrote and leaves no history; the host calls off a gesture an instance still holds open when it closes, so a gesture held open until something is decided, such as the infinite canvas's new text that is kept only once it is written in, never outlives its editor. An editor that keeps a copy of its own, as the text editor keeps a mirrored copy of its text, calls record() on the projection (and stop_recording() while it keeps none) and reads take_projected(): each foreign edit the projection applied as it came (Projected::Applied) or a change it could not apply on top of what the editor holds, such as a peer's edit rebased under edits the host has not acknowledged yet (Projected::Rebuilt), after which it re-reads the content. Another block's content is editor.content_of::<C>(block), the same projection keyed by that block. guides/reactive.md says how. Local-only view state is a signal the component makes; state worth keeping for this viewer, such as a scroll position or which folders are open, goes in the editor's view block through editor.view_state(key) and editor.set_view_state(key, state), and work that is neither - a snapshot to recompute, a picker's answer to collect - is an effect over the signals it reads: nothing in an editor runs every frame. What the host answers to a request arrives in the callback handed to editor.then(asked, answered) (see Asking the host, below), and what the host says unasked arrives as signals on the Editor at the top of the frame it was delivered for - editor.drag() and editor.files() for drops, editor.audio(), editor.history(block) (undo/redo availability and the saved head), editor.focused_block(), editor.web_view_events() and editor.peers::<P>() for the rest - and projections and graph reads track, so an effect or memo that reads them runs again when they change. Something that genuinely moves with time, like playback, is a beui create_timer that stops once it has nothing left to do - editor.audio() changes only when playback starts, pauses, seeks, ends or fails, so the position it carries is where playback was then and the audio editor advances it on its own clock - and work finishing on another thread wakes the editor through the Waker from editor.woken(), whose signal an effect reads to collect the result. Whether the host says the block is editable is editor.editable(), a signal written before every frame, and editor.read_only() is the memo a disabled prop takes. A link to another block is <BlockLink editor block>, handed the Editor and an Option<ChildTarget>: it follows that block's name and icon and opens it in the host when it is clicked. Icons come from beui::icons, drawn with the Lucide icon font every beui context carries.
- crates/editors/foo/manifest.json — the plugin's identity and everything the host is told about it (see below).
- Root Cargo.toml — add "crates/editors/foo" to members.

The plugin framework is three crates. crates/block-editor-plugin is the core, and knows nothing of any ui framework: it speaks the plugin protocol, keeps each editor instance's EditorHost, gives every screen the host asks for a surface of its own, and owns the wgpu device behind them. It hands each instance to a block_editor_plugin::Plugin, whose Instance is told the lifecycle (connect, creation, artifacts) and is asked to open_region the first time the host shows it a region (Frame, Preview, ArtifactSettings, Display(n), a further display of a desktop host, which shows the frame on its first display, or Window(w), a window the plugin asked the host for). The instances of one wasm module share a block_editor_plugin::Module (EditorHost::module; module.local keeps one value of a type for the whole module), and the module has one block_editor_plugin::Regions handler, which the first instance to open a region registers with EditorHost::handle_regions; the core sends every region's calls to it, not to the Instance. Each call names its region with a Region (instance, region, the instance's block, the region's rect from its own corner and the offset of the part its surface shows, scale, pixels, age, spec, describe, seen; Region::id is the RegionId, instance and region). The handler is given the protocol's TimedInputs for a region (ui-types' Input, the raw input a platform hands beui, with the time a pointer sample happened), with the RegionId of the region the pointer is over when a press made in this region holds it over another of the module's regions (the protocol's `over`: the event's position is then in that region's coordinates; over none of them the host sends PointerLeft and goes on in the holder's coordinates), and is asked to frame every region the host shows at once, frame(&[Region]) returning a Frame for each in order, so one frame of the module serves them all and a region the host has just asked for is drawn in the same call. A Frame says anything changed, when to be drawn again, the rectangles the host is told about, what it asks of the host about the windows it shows (asks, the protocol's window-requests, which the core sends in the FrameCommit), and its WindowRequests: the cursor, whether it holds the pointer, the IME area, whether it handles back or wants the keyboard, its intercepted keys, the paste kinds it takes and keyboard_toggles, the count of toggle_keyboard() calls that the host answers by opening or closing its on-screen keyboard, which the core reports in the frame it commits (FrameCommit's windows) for that region only when they change; the IME area's keyboard is Keyboard::Held or Keyboard::Shown { asks }, where asks counts the taps that should bring the on-screen keyboard back), and the handler is then asked to paint the regions that changed, each into a PaintTarget (paint(region_id, target)): the device, the queue, the view and format of that region's surface, its size, and its age. The Region an update is given carries the same age, so an instance can settle what it will repaint before it paints. At age 0 the core has cleared the surface and the instance paints all of it; otherwise the texture still holds what the instance painted into it that many presents ago, so it need only repaint what changed since. paint returns the rectangles it drew into, which the core reports with the frame so the host redraws only those. It also runs the host's run-action and node-action calls for a region, and answers painting and overflows for a test's or a driver's paintings. Around the module's frame the core prepares each region on its instance's EditorHost and collects what the frame left there (EditorSession::begin and finish): the drag and file drop over it, the chrome and placed content of a Frame, the settings draft of an ArtifactSettings region (EditorHost::settings_draft and set_settings_draft), and the children, occluders, content and frame requests the instance reported while EditorHost::in_region(region, ..) named that region. Rectangles cross between the host and the instance as they are, since a region's own coordinates are the instance's. crates/beui-platform-plugin is beui's platform for a plugin module: a beui_core Platform and PlatformServices like the other platforms. beui_platform_plugin::launch(host, options, context, app) runs PluginPlatform, whose Platform::run starts beui's Runner for the module's one App and registers it as the module's handler (ModuleRunner) and returns, the way the web platform registers its animation frame callbacks; the host's calls then drive frames. It never reads the BEUI_* variables the facade's run functions choose a platform by. The platform shows no main window. It opens only the windows it placed (WindowHosting::Placed), unless a region the host shows says the host shows the windows opened from it as windows of its own (Region::windows, the screen request's `windows`; block-app says so for the desktop shell's regions): then the module hosts every window (WindowHosting::Any), and a Window that is not one of the views (a dock window, a window opened `AtPointer` or `Over` another) is asked of the host with an `Open` naming the region it was opened from (Frame::asks), and so are its BeginMove, BeginResize, Resize and Close. The host shows it as a `Window(w)` region of that instance, `w` being the beui WindowId's number; the platform matches that region to the window, reports its size and scale as Resized and Scaled, the region's `placement` as Placed, input with Input::Focus as Focused, and the region going away as Closed. Views lists only the views, and Views::floated the window regions with their windows, whose reports block-editor-beui makes as it does a view's. and it hands the app a Views handle through Setup (setup.get::<Views>()): the View of each region the host shows (its RegionId, block, size in points, scale, the ratio from the host's units to the app's points and its FrameSpec), a watch that hears every change before the frame that brings it lays out, placement(id), the WindowPlacement to open that region's Window with, and report(id, Report), which takes a window's content, painted, floating and drawing rectangles, every_sample and press claims, in points, for the platform to turn into that region's Frame in the region's units. The app opens a Window per view with the view's size, so the window lays out at the region's size in the frame that first shows it, and the platform matches the window's Open to the region before that frame returns; it reports no placement for any window, so a dock can never reopen one, and a window opened any other way is an overlay inside the region it was opened in. The ModuleRunner pushes the host's input into beui's runner in its region's window, turns a region's Input::Focus into the window's Focused report, answers copy, paste and file picks through the EditorHost of the region that last had input, the cursor and the IME through its window, and paints each window with beui's wgpu renderer into its region's surface, keeping the damage of the presents before so it repaints only what the texture's age needs. A panic anywhere in the app stops the whole module, whose every region then reports it. crates/block-editor-beui is what every beui editor goes through: it implements Instance (BeuiPlugin<A> for a BeuiApp), whose open_region adds the instance to the module's one beui app on beui-platform-plugin (launching it with the first), which opens a Window for each region the host shows and builds the region's view into it (a Display(n) region with BeuiApp::Display(editor, display), empty unless the editor draws something on every display, as linux-desktop draws a bar), adds the editor's own pieces on top (Editor, the frame's chrome and menu, children), and re-exports the core, so an editor depends on it alone. An editor that wants no ui framework at all implements Plugin, Instance and Regions itself against block-editor-plugin and names its type in block_editor_plugin::plugin!("../manifest.json", { triangle => Type }); crates/editors/triangle is the example: its block holds no state (triangle_types::TriangleContent in crates/editors/triangle/types, a root with no fields), and it draws one triangle with plain wgpu into the middle of each surface, asking to be painted only until it has been. Its tests drive the Instance and the handler it registered (Module::take_handler) directly and assert on what it asked of the EditorHost.

Pointer input reaches an instance as TimedInputs, and a PointerMoved, PointerButton, Touch or Pen carries time_micros: when the sample happened, in microseconds on the clock DrawFrame's now_micros counts (block_editor_plugin::instant_at turns it into an Instant on the plugin's frame clock). The host sends one InputBatch per screen at a time: while one is still queued, the next is merged into it rather than queued behind it, so input never backs up a frame at a time and is never dropped. By default the host keeps only the latest move of each pointer (mouse, each finger, the pen) between two other events, with that sample's time, so an editor that only follows the pointer is not handed a backlog. An instance that needs every sample, as a drawing tool does for its stroke, reports FrameReport::every_sample (Frame::every_sample; beui's `every_sample` on an Interactive sets it), and while it does the host sends every sample, InputBatch::every_sample marking batches that kept them.

On the host, each region an instance is shown in is a retained beui component, PluginRegion in crates/block-app/src/compositor/region.rs: it mounts the screen for as long as it is built, places it from the Embed it fills, draws the screen's pieces, and gets its input forwarded by beui (Interactive's on_forward and forward_at, which leaves the holes its live children sit in to them). crates/block-app/src/compositor/editors.rs builds tabs, frame takeovers, embedded children and previews out of it, and what a plugin sends reaches them as one revision signal per plugin, so nothing on the host walks the editors each frame.

Editors draw with crates/beui, the project's own retained-mode ui. The plugin system is events in and pixels out - the host sends the input it routed and the plugin hands back the surface it drew - and beui is only what the framework puts in between. The framework runs one beui Context and one Document for the whole plugin module, opens a window of it for each screen an instance is given, builds <A::View editor /> into the instance's frame window once, and paints each window with beui's own wgpu renderer straight into its screen's surface, which the host composites. Colours are written the way the surface wants them: the plugin surface is not an sRGB format, so beui encodes gamma there and linear where it draws its own window. A region knows nothing of the monitors it is shown on: its overlays are laid out inside its window. A plugin that lays something out per monitor, like linux-desktop's bars, reads the monitors from an extension that describes them (be3:linux-desktop's DisplaysWatch, whose rects are in the region's points; see guides/linux_desktop.md, Displays).

A plugin carries no fonts of its own and may open no font file: the host sends the fonts it uses itself (the host interface's fonts-watch) as soon as the plugin has connected, and block_editor_beui::fonts() is the one beui::FontLibrary every context of the plugin is built over. A character none of those fonts covers is reported back (missing-characters), and a native host answers with a system font that covers it - found through fontconfig on Linux, or by looking through the system's font directories elsewhere - which the library adds and every region lays its text out again with. The web host sends its fonts but has no system fonts to offer. Tests never see a system font: block_ui_test's harness uses the fonts beui bundles (beui::FontLibrary::bundled()), so snapshots paint the same on every machine.

What an editor gets is the whole frame, and the framework draws nothing across it. What the host asks for with FrameSpec::top_bar (TopBar::Shown on a desktop, TopBar::Phone on a phone, TopBar::Hidden for none) is the frame's menu: undo, redo, rename, share, the command palette, the editor's own commands, file details, and Close when the frame belongs to a child that took it over, which Escape also leaves. The framework describes it to the host as a tree of MenuEntry values (the shell interface's menu call, which carries it flattened as menu-item values with a depth; MenuEntry::flatten and MenuEntry::nest convert): commands (MenuCommand: id, label, glyph from beui_core::icons, enabled, its first shortcut as a KeyChord, MenuCheck::Checkbox or MenuCheck::Radio with its tick, MenuPin::Icon or MenuPin::Label for a command the dock bar shows beside the More button instead of in it, and MenuPin::Title for the one a phone's stacked bar runs when its name is tapped), submenus (MenuSubmenu) and separators, nested at most MAX_MENU_DEPTH deep. It sends the whole tree again whenever an entry changes, so the host never polls, and runs the command whose id the host sends back (MenuPick), wherever it sits in the tree. The protocol knows nothing of beui, so any framework can fill it. The instance that placed the block reads it as ChildBlock's handle.menu, MenuNodes of detached actions that pick from the child (their labels, enabled states and ticks update in place; the tree is rebuilt only when its shape changes), and the workspace hands them to its dock with dock_menu, adding before File details what it knows of the block and the editor does not: References and Referenced by, submenus that open each related block, and Access, which previews the block as someone who can only view it or cannot see it. So the same menu is behind the More button of the block's tab on a desktop and of the stacked bar on a phone, where its submenus open as pages of the sheet. Undo and redo are pinned as icons and Share with its label, so they sit in the tab bar beside the More button rather than in it (an action takes .pin(Pin::Icon) or .pin(Pin::Label)); on a phone the stacked bar keeps undo and redo and leaves Share in its menu, and Rename is pinned to the title (Pin::Title), so tapping the block's name renames it, so an editor draws no undo or redo buttons of its own. The menu's commands are actions (see guides/beui_keyboard.md, Actions and the command palette), so undo owns Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y for the block while the host asks for the menu, after the focused control has had the key, which is how a text area keeps its own undo, and Ctrl+Shift+P opens the frame's command palette over everything the editor registered. File details asks the instance that placed the block, which hears it through ChildBlock's on_bar (BarAction::Details). The system back gesture, and the Back key, reach a plugin's BackHandlers too: an instance tells the host whether its document has one enabled through its WindowRequests, and the host sends back to the last screen it drew that has one, unless its own document handles back first, so an editor's open sheet closes before the workspace leaves the file. Shortcuts that must reach an instance whatever has the keyboard - a program's window, another plugin, the host's own controls - are its intercepting actions (see guides/beui_keyboard.md): its WindowRequests carry their chords as intercepted_keys, and the host offers those chords ahead of whatever is focused and sends each press it takes, its repeats and its release to that screen as InputEvent::InterceptedKey, after the Modifiers they were made with, then keeps sending Modifiers until the chord's modifiers are let go; a tap chord (an action on Chord::tap) is sent as InputEvent::InterceptedTap while the screen does not have the keyboard. block-app does this for the shell's frame only. A screen whose document has a layer open that traps focus reports WindowRequests::wants_keyboard, and the host gives it the keyboard until it clears, then hands it back. An editor adds its part of that menu while its view is built with add_to_menu(vec![MenuNode::action(&action), MenuNode::submenu(id, label, glyph, items), MenuNode::Separator, ..]) over actions it registered; the part goes when the scope that added it does, and the framework puts it between its own commands and File details. An action made with .checked(signal) is a checkbox there and one made with .radio(signal) one choice of a group, ticked while the signal holds. That is how the canvas and the text editor offer the commands that do not fit their own bars instead of a toolbar; the canvas builds its frame menu and its context menu (ContextMenu with <MenuNodes nodes />) from the same submenus in app/menu.rs. Every action, in the menu or not, is also in the command palette, and the buttons and menu rows that run it take it as their action prop, so all of them share its label, its enabled state, its tick and its shortcut. A dialog creation instance gets the dialog's whole plugin rectangle through creation_frame, and an editor that declares the Preview region writes one more component, BeuiApp::Preview, which the framework builds into the preview's own window - with a second Editor of its own, so the two regions place their children apart - when the host shows that region. The counter editor is the smallest example, checklist shows a larger retained document, the deterministic game shows dialog creation with a block picker, and the presentation editor shows children, playback and a preview.

An editor draws its own chrome inside that frame rather than being called back for one band at a time. What it is told instead is whether the host is showing this instance's chrome at all this frame - editor.chrome_shown(), a signal the framework writes before every frame - and an editor with a sidebar of its own hides it when that reads false, which is what keeps the same code right for a tab of its own and for a block being edited live inside a canvas. Because the host cannot see where an editor put that sidebar, the editor names the node its content is in once, with editor.content(&node_ref), and the framework reports that node's rectangle after every layout; that rectangle is the one the host pans, zooms and reads wheel gestures against, so a wheel over the sidebar is not a wheel over the content. The band itself is <Sidebar shown={editor.chrome_shown()}>, a block_editor_beui component the editors share: it takes the side it sits on, scrolls what is written between its tags, draws the border against the content, and leaves the row it is written in while shown is false (it is a ShowKeepAlive, so the row needs no other change and its scroll position survives), giving the whole frame back to the content. Toolbar's shown works the same way, so both are written among the children of a List. On a frame narrower than NARROW_WIDTH it leaves the row altogether: its contents move into a Sheet under the content, opened by a toggle the framework adds to the editor's Toolbar, whose buttons scroll sideways there instead of wrapping (or to a bar of its own when there is none, or to the frame's menu on a phone); sheet_control() opens it from an editor's own button. narrow_chrome() reads the same test for an editor that wants its toolbar compact there. That is only the frame's width, which a desktop pane can be too; phone_layout() says the app itself is on a phone (the host asked for TopBar::Phone). Prefer one layout that works on both over one meant only for phones: the canvas keeps its tools in a BottomDock over the stage, with the selection's tools in the row above it, and the text editor keeps its formatting in a bar that shows while the text or the bar itself has the focus (so Escape, then Tab, reaches its buttons, and the arrows walk them), which is an Interactive with press_focus=false so pressing anywhere on it, its format buttons included, leaves the focus, the selection and the keyboard in the text (its Done button then clears the focus on purpose); its button that puts the keyboard away shows only when a finger focused the text (TextAreaState::touch_mode), since only then is there an on-screen keyboard. The database, worktree, game module and audio editors are the examples.

An editor whose layout is a dock of tabs - the workspace is the one that does this - builds it with beui's Docking inside its own frame; the dock and any window popped out of it live inside the plugin. A dock in an editor placed inside a tab of another plugin's dock joins that dock across the plugins, as one dock nested in another does in-process (guides/beui.md); the protocol for it is in crates/block-plugin-api/PROTOCOL.md (the paragraph starting "Docks cross plugins"). block-editor-beui does the plugin's part with no code in the editor: a ChildBlock built in a tab's body places its child with child-placement.docks naming that tab (the first ChildBlock of a tab only), and the dock of an instance whose frame is requested `docked` declares itself through EditorHost::declare_dock instead of drawing, its tab bodies built where the host shows each tab's Tab(t) region and kept while the root holds the tab; the dock of an instance that is not docked is the root for its children's, and hosts each one's declaration (EditorHost::child_dock) as a pinned group in place of the tab, as an in-process join, placing a Subregion of SubregionContent::DockTab for each of its tabs' bodies. A docked tab body's dock_menu and use_dock_tab() work as in a local dock: its menu, followed by the frame's menu, crosses as the dock-tab's menu (a pick comes back as the frame's MenuPick), and its DockTabControl (DockTabControl::hosted) shows the tab, reads focus and fullscreen, and asks for fullscreen through dock requests. The placer frames each of its child's tabs with ChildBlock's docked_tab, handed the tab's menu and body (ChildDockTab), by default only giving the menu to dock_menu; the workspace's BlockPanel puts its block menu on that menu and its bars (artifact, deleted, linked, revision preview) above each body, so every tab of a joined block carries them wherever it is moved. A child placed in a tab's body keeps its child id when the body moves between regions, since the core keys it by the tab rather than the region. block-app routes it between the instances (crates/block-app/src/plugin_host/docks.rs). The host's own debugging panels (HostPanel: the block stack, performance and plugins) are drawn by the host but placed by the workspace: the app menu asks the shell to show one (take_panel_requests), and the workspace declares it as a window of its dock holding a <Subregion placed={Some(SubregionContent::Host(panel))}>. The host knows a panel is wanted while some plugin places it. The windows of the programs the host runs are placed the same way: on Linux the app is a Wayland compositor (crates/be-wayland, glued in by crates/block-app/src/wayland.rs), editor.watch::<WindowsWatch>() is the list of its windows with their titles, parents and drawn sizes, and the workspace gives each one a tab - or, for a window with a parent, a DockDialog attached to the parent's tab (block-shell's AttachedWindow; linux-desktop floats its top windows in dock windows instead of tabs) - holding a <Subregion placed={Some(SubregionContent::Window(id))}>, which the host draws and sizes the program to. A window the program marks modal (xdg-dialog-v1's set_modal) is listed with modal set and its dialog is modal to its parent; the host keeps presses and keys from the parent on its side too, giving the keyboard to the innermost modal dialog instead, and the dialog's window tab asks for the keyboard (WindowAction::Focus) when a press lands on the parent in the plugin. Closing the tab asks the program to close (WindowAction::Close); the tab goes when the program's window does. A listed window is focused while the program has the keyboard, and the workspace's window tab then shows itself in the dock, so the dock's recent tabs follow the keyboard; when the dock focuses a window's tab some other way (a commit of the switcher), or gives it the keyboard (a press on its bar, its tab or its grips, even while it is already focused, which `DockTabControl::keyboard` counts), the tab asks the host to give the program the keyboard (WindowAction::Focus), which also raises it. The press itself reaches the plugin's region, which takes the host's keyboard until that request arrives. The host keeps forwarding a press to the region it began on, and a lost keyboard (Input::Focus(false)) ends no press, so a tab being dragged out of the window's bar goes on; a press the host gives up reaches the plugin as Input::PointersCancelled, a touch's cancel or the pen gone (guides/beui_keyboard.md). A listed window's raised counts the times the host brought it forward (WindowAction::Focus, a program's xdg-activation request, going fullscreen, a press on the window); the workspace shows the window's tab each time it goes up, even while the tab is hidden behind another and its panel was never built, and the program gets the keyboard once its tab is drawn. Raising a window that has a modal dialog raises the dialog instead, and raising a dialog shows the tab it hangs from. The host only draws a window for the instance that draws the app's window. A window that wants to be fullscreen (the program asked, or linux-desktop's Super+F toggled the focused one with WindowAction::Fullscreen) is listed with fullscreen set to the rect of the screen it was on, in the plugin's coordinates; the workspace's window tab then makes its dock tab fullscreen over that rect (see the dock in guides/beui.md), and if the dock lets go of it first the tab asks the host to take the window out of fullscreen (WindowAction::Fullscreen). Maximize only tells the program it is maximized; it already fills its tab. linux-desktop gives its dock `drag_modifier` Super (see the dock in guides/beui.md), so Super+drag anywhere on a floating window moves it and Super+right-drag resizes it, or moves the split beside a docked one. For that the press has to reach the plugin rather than the program under it: block-editor-beui reports the document's `press_claims` with every frame (`Frame::claims`, `FrameReport::claims` in the protocol), the host's PluginRegion claims those presses for the plugin with `claim_at`, which also keeps them from any child editor there, a program's window among them, since each window is a forwarding catcher like a plugin's region (guides/beui_keyboard.md, One input path). A client's own `xdg_toplevel.move` and `resize` requests (dragging a client-side titlebar) are not honoured yet.

While a screen reader is on (the platform asked the host for its accessibility tree) or a driver is attached (guides/running/drive.md), the host calls the plugin's describe(true) export, and every Frame region's FrameReport then carries a Description: an AccessKit TreeUpdate of the editor's accessibility tree (on the wire the accessibility interface's tree-update, crates/block-plugin-api/wit/accessibility.wit, which mirrors AccessKit's node properties; block-plugin-api converts it back), and the actions it registered (guides/beui_keyboard.md). The tree is in the region's coordinates (points, from its top-left corner) and uses the editor's own node ids. It is incremental: the first after Region::describe changes is the whole tree, each later one only the nodes that changed, and None when nothing did. Region::describe is None while nobody is listening and changes whenever the host needs the whole tree again (describing turns on, or the region gets a new screen); block-editor-plugin keeps the trees of frames it has not reported yet, so none is lost. The host keeps a copy of each region's tree (beui's `accessibility::Embedded`), renumbers its nodes into its own, cuts it into a valid tree whatever the plugin sent, and shows it as a Pane named after the plugin under its window, with the editor's focus while the region has the keyboard. beui-platform-plugin fills it from the part of the document's accessibility tree in the region's window (FrameOutput::window_accessibility_tree), which carries the test ids, so a beui editor needs nothing more than the labels and @test_ids it already has, and an editor on another framework fills Frame::description with AccessKit itself, as it would for a window of its own. The host calls back node-action with the screen reader's ActionRequest (the accessibility interface's action-request) in the editor's node ids, and gives the region the keyboard for an action that moves the focus into it (focus, click, setting a value); run-action runs one of the editor's own actions. beui-platform-plugin carries out both.

The view itself arrives in beui's own coordinates as signals on the Editor the component was handed: editor.canvas() for the beui::reactive::CanvasView a Canvas takes and editor.scale() for what the content is being shown at, both written before every frame, with editor.pan, zoom and reveal - which pans a rectangle of the editor's own world into the middle of the content - to ask the host to move it, editor.fit, which fits a rectangle of the editor's world into the view through those, and keep_fitted, which declares what the host keeps fitted as the frame changes (guides/pan_and_zoom.md). The host still owns it, so those work the same in a tab and inside an infinite canvas. beui's Canvas is what puts the content where the view says: its CanvasItem children carry a rectangle in the editor's own world coordinates, and the canvas maps each one through the view, clipping and culling to the rectangle it was laid out at. A canvas never told where its view is fills the space it was given at a scale of one, and one given a width and a height reports that as its size, which is what lets a canvas of absolutely placed items sit inside a Scroll. Placing an item is not transforming it, so text inside one keeps whatever size it asks for: an editor whose content should grow with the zoom reads the scale and sizes its own text by it. The pan and zoom editor is the smallest example of all of this, and its block stores nothing at all.

Testing one is block_ui_test::BeuiTest: it is built from an Editor, or from a Creation for a dialog, and runs it through the same plugin session the shipped plugin runs (block_editor_plugin::headless), speaking the plugin protocol to a stand-in for the app's host that holds each block's content in a replica of an in-process block_type_guest::Module, the way the app hosts it, and attaches the editor to a block's replica on the first Replica frame it sends for it; so a test holds the same handle the component was handed, and reads what the plugin sent the host (view requests, opened blocks, host requests) back off the BeuiTest. It drives the app with drive's gestures, sent to the plugin as the host would send them, through the methods beui's testing::Harness has, with its targets (a test id, which it scrolls into view first, or a point) and argument order: click, click_with, double_click, hover, down, up, drag, scroll, tap, fingers, type_text, key, key_down and key_up. It keeps the drive commands those amount to (steps()), and its own failures print them. Its snapshot is what beui's renderer would hand the gpu for that frame (beui::quads): the rounded rectangles and glyphs it turns into instances, each glyph carrying its own coverage image rather than a place in the atlas. No gpu draws it, so no driver can change it. guides/testing_a_gui.md says how they are run.

A plugin has no connection, no block store and no key of its own: the app is the only peer, and a plugin reaches blocks only through the host. Content arrives as the ContentProjections above. The graph - which blocks exist, their names, parents, references and access - is the host's mirror of the server's, and a plugin asks about it with editor.watch_blocks(query), a memo of the BlockInfos the host answers a BlockQuery with (Roots, Detached, Shared, Children, References, Backrefs, Parents or one Block; nothing lists every block, so a plugin that offers blocks to choose from browses a folder at a time from Roots and Shared), and changes it through editor.blocks(), a Blocks handle: create, create_named, create_artifact and create_with make a block with its first content, set_parent moves one, set_name names one by hand, define sets any other defined metadata key, info and access read what the host last said, and watch is the query as a BlockList without the memo. editor.create_child(&content) is create under the editor's own block. Each of these is a GraphCommand the session sends the host as a create-block, set-parent or define call of the be3:plugin blocks interface; the host applies it to its mirror straight away, checks the account may edit what it touches, and hands it to the app's peer, which carries it to the server. Because the peer belongs to the app rather than to the instance, a block an instance has just created still reaches the server after that instance closes.

What the EditorHost (editor.host()) offers, for anything the plugin cannot do itself:

- open_block(id, block_type) — opens another block in a tab of its own.
- block_types() — the host's registered block types, for naming and illustrating a block this editor only holds a reference to. Pass it to block_ui::BlockLabel (re-exported as block_editor_beui::block_ui) so labels match the rest of the app, including how an automatic name is italicized.
- editable() — whether the block this instance was opened on may be edited, so an editor does not write back what it worked out (an image's decoded size) on behalf of a reader. The host cannot disable a plugin's own surface the way it greys out an editor it draws itself, so an editor whose block may only be read keeps every gesture that would change it behind this: the pixel art editor still pans, zooms and reads out pixels, but draws nothing and disables the buttons that would.
- drag() — the block the app is dragging over the screen being drawn, in that screen's own coordinates, and whether it has been let go. Draw the drop feedback yourself and answer accept_drag(bool), which decides the cursor the host shows. A drag that starts and ends inside the editor's own document - a card between columns, a slot in a hotbar - never reaches the host: that is beui's Draggable and DropTarget (guides/beui.md).
- Files are picked with beui's own picker (guides/beui.md, Picking a file), not through the host: inside a plugin, beui forwards the request to the host's picker and hands the answer back, so the same code works on desktop, Android, the browser and in a plugin. block_editor_beui::FileChooser, a Copy handle owned by the scope that made it, adds the import step, the chosen file's name and the error to show, and on_chosen(...) to take what was imported.
- save_file(file) — the other direction: the host saves a SavedFile (a name, a MIME type and the bytes) through the platform's save dialog, or as a download in the browser, and answers a FileSave: saved, cancelled by the person, or why it failed. export_block(block) saves a block and everything inside it as a block file the same way; the file tree's Export is the example of both.
- read_plain_file(block) — a block's plain-file form, which its type module gives (`replicas.to-file`, guides/type_modules.md): the host answers a SavedFile named after the file it came from, or the block's name with the extension the type chose, or the reason it has none. A type with one has `plain_file` set in block_types(). Reading it and then saving it is the file tree's Export as for any such block; exports that render (a PNG, a PDF) are the editor's own and go through save_file.
- load_audio(media_type, bytes), play_audio() and reset_audio() — sound the host plays for the editor, reported back through editor.audio() as an AudioStatus. Load hands it the encoded file (an AudioCommand::Load of an AudioSource), play_audio toggles playing and pausing it, and reset_audio stops it and drops it. The host decodes only the media type, never the block, so an editor loads its bytes again after its content changes; the audio block loads them on the first play after each change.
- fetch(url) — a GET the host makes on the plugin's behalf, answered with the body or why the attempt failed. Canceling it (its Task, or closing the editor) aborts the request in the browser and drops the answer natively. A plugin has no network of its own on any platform, so this is the only way it reaches one, and the host refuses any URL whose host name the manifest's network list does not name. The map editor downloads its tiles this way.
- list_data() and read_data(path) — the read-only files the plugin was staged with: their paths, and one file's bytes. A plugin has no file system, so data it ships rather than keeps in a workspace goes in the `data` of its BUCK file's `editor()` call, a map from a relative path to a source or target; the build stages it beside the app under data/<plugin id>/, and the host reads it from there on every platform. The games editor ships every game module this way.
- editor.pick_block(filter, anchor, picked) — the block picker, which is how an editor acquires a child without waiting for one to be dragged in. The filter names what is being chosen, the block types that may be chosen, empty for any, the blocks never offered (the editor's own is added), whether the picker opens on the templates the host offers rather than on its new-block menu, and where to place what it makes; anchor is a PickAnchor, made from the NodeRef of the button that asked, a Rect in the editor's own coordinates, or Option<Rect> (None centres it). The SDK places a picker child (SubregionContent::Picker) there itself: after a touch, or in a phone layout, it fills the frame and the picker draws its menu and cards as sheets; otherwise it is a popup Window under the anchor (above it when only there is room), sized to what the picker measures (editor.fit_to(Some(node)) reports a node's natural size, or an overlay's content's, as the intrinsic size each frame), which block-app draws over the app so it reaches past the editor's frame. The host runs the child in the editor that accepts pick (workspace-ui's picker, block-shell's Picker and PickerView), which browses the graph itself; picked is handed the block chosen, linked or created, or why it failed, and nothing when the user cancelled; a new pick replaces the one before it. Creation::pick_block does the same in a creation dialog, which is how an editor whose block cannot be made until it references another one - the game editor, which plays a game module block - gets that block before its own exists. A test answers it with BeuiTest's placed_picker() and answer_picker(pick), and tests the picker itself with BeuiTest::picker or picker_beside and take_picked().
- Asking the host: every EditorHost function above that the host answers - save_file, export_block, read_plain_file, fetch, list_data, read_data, and the shell's list_access, contact_link, import_blocks and the revision calls - is an async function of the host-services interface (crates/block-plugin-api/wit/host-services.wit), called for the editor's own instance, and returns an Asked<T>: a future of the answer, or None once the call was canceled. A call that can fail answers a Result whose error is the protocol's Failure (types.wit, block_plugin_api::Failure, which the plugin's own commit-creation and regenerate-artifact answers too): denied (the editor may not see or change what it asked about; the host refusing the call as a whole folds into it), unavailable (no such service or nothing to do it with, now), or failed with a message for the user; its Display is the text to show. editor.then(asked, answered) (EditorHost::then underneath, Creation::then in a creation dialog) runs it and hands the answer to answered if the scope that asked is still alive, and returns a Task whose cancel() withdraws the call. Closing the editor cancels everything it still waits on: the host drops that work - a fetch, an import or export not yet made - and answers canceled. A test stands in for the host with BeuiTest's take_requests(), the calls the editor made as block_ui_test::HostCall, each carrying the Reply that answer(reply, value) answers it through.
- present(on) and presenting() — asks the host to give this instance the whole window with no chrome bands and show nothing else of the app, and reports what the host settled on. The host owns the answer: it takes presenting away when the user presses Escape or the instance stops being the one on screen, so an editor reads presenting() rather than remembering what it asked for, and draws its content the same way either way.
- open_web_view(id, url), load_web_view(id, url), reload_web_view(id), focus_app(id), close_web_view(id) and take_web_view_events(id) — a web view, which the editor places with <Subregion placed={Some(SubregionContent::WebView(id))}> and whose events (the address, history changes, a failure) it reads back: the browser tab editor turns them into the history its block keeps. No host shows a web view yet. The app answers every open with a failure, which the editor shows in the view's place, until an embedded browser replaces the system web view it used to open.
- Holding the pointer is not a host call but WindowRequests::pointer_locked, which asks the host to hold the pointer still and hide it, which is what an editor that looks around a scene wants: while it is held the editor reads PointerMotion events rather than a position. The host holds it while any screen of any instance asks and lets go as soon as none does, so an instance that closes cannot leave the pointer trapped; the editor still lets go itself on Escape or when it loses focus. A beui editor writes unstyled::PointerLock (guides/beui.md) and its region's WindowRequests carry what the context asked, and the framework turns the host's PointerMotion and Focus events into beui's, so the control reads motion rather than a position and lets go on Escape or a lost focus without knowing there is a host at all. The scene_3d editor is the example.
- Frame::stopped says a region will draw nothing more: Stopped::Closed when its app closed itself, Stopped::Failed with the panic when it failed. The core sends it to the host once as the shell interface's region-stopped call, and the host shows the error in the region's place with a restart, rather than a blank screen; a beui region says it when its Runner exits.
- watch::<W>(), offered::<W>() and act(call) — what only the host can see and do. W is a watch resource of the WIT world (a resource named *-watch with constructor() and next: async func() -> T); be-ops-bindgen implements be_ops::Watched for each (re-exported by block-editor-beui with block_plugin_api's), naming its value type, so editor.watch::<W>() is a memo of the value, its Default until the host answers, and editor.offered::<W>() a memo of whether the host has answered at all. The first read opens the watch under the editor's resource, and the host answers its next with the value at once, whenever it changes and again after the plugin restarts; the EditorHost keeps a revision per watch, bumped only when its value changes, so a push of one wakes no watcher of another. The core ones are in be3:plugin's account interfaces (wit/account.wit): AdministratorWatch, LinkBaseWatch (the URL of the server the organization is on, which block links start with, empty for the device's own server; see be_block::block_url) and PreferenceSourcesWatch for any editor, and ContactsWatch (the account's contacts, for the shell's share dialog, which lists who it may share with again whenever they change), which the host answers only to the shell, the instance drawing the app's window (main.rs names it with PluginEditor::claim_shell). The Linux desktop session's are the be3:linux-desktop extension (guides/linux_desktop.md, The host's side), which only a plugin whose manifest names it in extensions may use: WindowsWatch, InputDevicesWatch, RemapsWatch, DisplaysWatch, PowerWatch, MediaWatch, WifiWatch, EpaperWatch, NotificationsWatch, ScreenLockedWatch, ProgramsWatch and TrayWatch, each a record of the extension's WIT re-exported at block_plugin_api's root (HostWindow, PowerAvailability, MediaLevels, HostProgram with a HostImage icon of plain RGBA pixels, ...). A host with no Linux session answers those watches unsupported, which the editor sees as never offered. What an editor asks of the host is a function of the same interface, called inside editor.act, which makes it under the editor's resource: editor.act(move || linux_desktop::power::request(action)), with linux_desktop the generated guest module block-editor-beui re-exports (windows::request(WindowAction), power::request(PowerAction), media::request(MediaRequest), wifi::request(WifiRequest), epaper::refresh(), notifications::report(NotificationReport), programs::request(ProgramAction), tray::request(TrayRequest)). On the host, plugin_host::publish::<W>(&value) sets a value and tells the instances watching it when its encoding changed, plugin_host::watched::<W>() says whether any instance is (the host starts PulseAudio only then), and plugin_host::take_calls(block_plugin_api::requested::power) takes what instances asked, read by block_plugin_api::requested's reader of that function. block-app's plugin_host/wire.rs refuses a watch or call of an extension the plugin's manifest does not grant (denied) or the platform cannot back (unsupported, plugin_host/published.rs); nothing else is listed anywhere. A new one is a watch resource or a function in the WIT, a publish or take_calls where the host learns or carries it out, and watch or act in the editor. A test stands in for the host with BeuiTest's set_watched::<W>(&value), watches::<W>(), host_calls(reader) and take_host_calls(reader) (block_ui_test::requested is block_plugin_api's), or sets a value on the EditorHost with set_watched::<W>(&value).
- occlude(rect) — declares that the editor draws over that rectangle after the children placed so far, so the host neither draws nor routes input to them there.
- close_dialog(answer), handles_dismiss(bool) and dismiss_child(child) — an instance shown as a dialog asks to be closed, accepting it or not, and says whether it answers a dismissal itself; an editor showing a child as a dialog passes a dismissal on to it (see below).
- take_show_requests(), take_panel_requests(), take_dialog_requests(), commit_child(child, parent, name), list_access(block) and set_access(block, account, access), report_focus(focused), watch_artifacts(blocks), artifact(block), regenerate_artifact/unlink_artifact(block), simulate_access(block, level), close_editor(block) — what the instance that draws the window needs and no other editor has any use for. The rename and share dialogs any editor's menu asks for (rename_block, share_block) are drawn by that instance: the host passes the ask on as a ShellDialog, and sharing lists and changes who has access through the host. rename_block takes the rect of the control that asked, if any, which the host moves into that instance's frame along with the block it was asked from, so the workspace hangs its rename card from that block's tab pointing at the control (a card in a narrow pane like the files reaches over the panes beside it), or from the top of the tab when nothing is pointed at; on a phone the card is a sheet. The card names the block, saving the name on Enter or when it closes, and sets its icon (any of beui_core::icons::ALL, searched by name and tag) and its icon color, or puts back its type's, writing that metadata itself as each is picked. The file tree renames a row in place and opens the same card from Icon and color…. The host hands that instance every block anything asks to open, including the blocks it asks for itself, so opening a block is one path however it started; it answers with the block the user is looking at, which the host then tells every other instance; it names the blocks whose dynamic artifacts it is showing and reads back what the host's own artifact instances describe; and it asks the host for the things only the host can do to a block it is not itself drawing - holding it to less access than the account has, and closing the editor of a tab that was closed.

What the host asks of an editor, beyond drawing, it asks through its `Editor`. `presence_visible()` is a signal the framework writes before every frame saying whether anyone is looking at this block, which is when a collaborative cursor is worth publishing, and `revealed()` asks it to scroll one of those cursors into view - only the editor knows where in its content that is. The cursor itself goes through editor.show(Some(&value)), with a value of a be_block::presence::PresenceKind, and editor.peers::<P>() is a signal of every other peer's value of that kind; host.show_presence is the same for a block other than the editor's own. It goes to the block's replica as a Replica frame, which shares it with the block's session and never saves it, and the host takes it away when the instance closes. The framework shows a UserActive entry of its own while the block is visible, and a peer never sees what it showed itself, so the presence an editor reads is only ever other people's - never a cursor for the person at the keyboard. A cursor carries its own colour, picked with pick_free_color against the colours the other peers are showing. `on_replace_child(...)` registers the answer to a block the host copied because it was being edited in two places at once; an editor whose references live inside its own content (the text editor's block URLs) rewrites them and answers true, and one that leaves it to the block's own structural edit answers false. That callback is made outside the document; signals it writes reach the view on the next frame, which the write asks for itself. beui has no IME output of its own yet, so an editor cannot report an IME area.

An editor never offers the frame's menu or the way out of its own frame. The framework offers both itself, so an editor cannot lose them. Which chrome an instance is given changes from frame to frame: the same code draws a tab of its own, a block being edited inside a canvas, and a slide inside a deck, and editor.chrome_shown() is how it tells them apart.

BeuiApp::intrinsic_size, or editor.set_intrinsic_size for one that changes, reports the size the editor wants wherever the host embeds it (a canvas, a text block). BeuiApp::aspect_ratio reports the shape of the block, which the host holds a preview to. Leave either unimplemented to take the host's default.

Drawing the block itself: an editor that lists Preview among its regions is asked to draw its block wherever the host paints it rather than opening it — a canvas entity, a slide, a block embedded in text. The host maps that screen onto the quad it is painting, straight from the plugin's surface, so Preview fills the screen it is given and lets the host place, rotate and fade it. It has no background of its own, so whatever is behind the block shows through. A frame is not: it is cleared to its Root's clear_color, and what shows through it are the holes cut for the children placed in it. Children placed in a preview work like children anywhere else, so an editor whose block is only its children - a presentation showing its first slide - draws them there as previews.

Placing something inside an editor: <Subregion> reserves a rectangle in the editor's view and asks the host to fill it with what its placed prop names, a SubregionContent - another block's editor (Block), one of the editor's web views (WebView), a panel the host draws itself (Host), a program's window (Window), a template being made (Creation, the editor and template id from the catalog's templates), the settings screen of a block's dynamic artifact (ArtifactSettings), or a block picker (Picker, which pick_block places for you; its answer arrives in ChildState::picked). A Creation child reports its progress in ChildState::creation - options, ready or not, then created or failed - and commit_child asks the host to make it, under the parent and with the name given; the picker is built on it. The host draws it there and every placement kind shares the geometry, layer and status described below. Embedding other editors: the <ChildBlock> component, a Subregion of a Block, puts another block's editor inside this one — another plugin, several levels deep. Every editor is a plugin, so a child is always another one of these. It takes the Editor it was handed, a block prop naming the block and its type (None while the reference has not resolved yet), the mode and layer the placement wants, and own_frame for a child that lays its own chrome out inside the rectangle. It reserves the space it is laid out in with beui's Embed base node, which reports the rectangle and the clip it was laid out in, and the framework turns that into a placement, one per frame, in the region being drawn. The subtree written between its tags is drawn inside that rectangle and is handed a ChildBlockHandle carrying a ReadSignal<ChildState> - placed, available, active, intrinsic_size, aspect_ratio, interaction, capabilities, resize and error - so a placeholder is a Frame whose visibility follows that signal rather than a branch in the view; on_state reports the same value to the editor around it, which is how a stage sizes itself to the slide's aspect ratio, and Frame's aspect_ratio prop is what fits a child of a known shape into the space a stage was given.

A child is drawn *under* the plugin's own surface and the space it takes is cut out of it, so anything the editor draws after the child — a selection handle, a drag ghost, a menu, a modal — covers it simply by being drawn later. A child that is genuinely translucent cannot composite that way and is placed with layer=ChildLayer::Above instead, which composites against the plugin's pixels and cannot be drawn over. Children are placed in the order they paint, and an overlay of the editor's - a menu, or a window of its dock - covers the children painted beneath it, for drawing and for the pointer, but not the children inside it.

A child placed with own_frame=true lays its own chrome out inside the rectangle it was placed at instead: it draws its toolbar row and sidebars there, and the editor that placed it keeps its whole frame and every band in it. Placed with a top_bar as well, it offers its parent the frame's menu, which is how every block tab in the workspace gets one while the pane of files does not. That is the other way to run an editor inside one - ChildMode::Live hands the frame over, own_frame gives the child one of its own - and it is what lets the workspace plugin put a pane of files beside the block being edited, each with its own toolbar over its own part of the window.

The editor keeps every click over a passive child: nothing is delivered to the child until the editor promotes it to ChildMode::Active, which is what a double-click or an Edit button does, and the host takes the promotion away again when the user clicks outside or presses Escape. A child that is not something the user promoted but the whole of what the editor shows - the slide a presentation is editing - is placed with ChildMode::Live instead, which is live from the moment it is placed and which the host never takes away. ChildMode::InPlace is live from the moment it is placed too, but never takes the frame: the child takes input where it was placed and draws no chrome, and when it is placed with an intrinsic size its layout keeps that size while the host renders it at the zoom the placed rectangle has over it, so it grows and shrinks with a canvas's camera rather than laying out again. A canvas places an editor with no camera of its own (a checklist) that way, and one with pan_and_zoom (pixel art, another canvas) passive until it is clicked. ChildMode::Preview asks for the other end of that: the host draws the block rather than running its editor, which is what a filmstrip of thumbnails wants. A preview child is composited over the plugin like any other child below it: the host draws the block's own preview into the hole, clipped to where the child was placed. A block previewed in several places at once, such as an image on a slide shown both on the stage and in the filmstrip, has one preview: the host draws it once, at the largest of those places, and each place shows its own part of that drawing. None of that is the editor's to arrange: place the child, ask for Preview, and draw the rest around it. ChildState is what the host made of the child: available is false when the block cannot be opened — a block already open above this editor is refused, and error says so — while intrinsic_size, aspect_ratio, active, interaction, capabilities and resize are what the host last saw. interaction is the child's own manifest answer, which is how an editor knows whether to run the child live or to draw it as a preview until the user asks to edit it; capabilities and resize are what an editor laying children out in a world of its own needs to know before it draws a resize handle. Tell the child what you gave it with the intrinsic prop, which reaches it as the size it was resized to, and place a preview child at an angle or faded with the rotation and opacity props. A child with a view of its own moves it the same way wherever it is placed, and the host answers against the frame above it that owns a camera, without involving the editor that placed it: a pan or zoom moves that camera, and fit fits the rectangle the child was placed at into it. When the host gives the keyboard to a child, or to anything placed inside it, it tells every instance above it which of its children that went into (the editor resource's child-focused method), and ChildBlock's on_focus hears it: the workspace selects the dock pane that holds the child, since a press inside a child never reaches the instance that placed it. Place only the children that are visible: the host runs a bounded number of them as editors and draws the rest as previews. An editor test only records the children an editor places; how the host runs them, promotes them and hands the frame back is tested against the app in crates/app-tests (guides/testing_a_gui.md, 6), and an editor that places children deserves one there.

A child the user has promoted to ChildMode::Active, or one the editor placed with ChildMode::Live, takes the frame over: it is handed the same frame this instance was, draws every chrome band in it, and draws its content at the rectangle it was placed at. The editor that placed it draws no chrome at all while that lasts: its bands go away and its content takes the whole frame rather than keeping a band of nothing where its toolbar was, so a canvas shows more of its world there. Its camera is untouched by that, so the world - and the child's own rectangle in it - stays exactly where it was on screen. The part of the frame the child paints its chrome over is withheld from the editor underneath, so a click on the child's toolbar or its sidebar belongs to the child; a click on the rest of the frame, which shows the editor beneath it, falls through to the editor that placed it, and that is what takes the frame back. So does a click on the child's own content outside the rectangle it was placed at, other than on its floating chrome: that part of the content is where the parent's world shows, and `editor.placed_content()` tells the child that rectangle, so a child that draws a world of its own (a canvas) clips it there. There is no way to nest a child's chrome inside a band of your own, and no way to keep a band while a child has the frame - a deck whose slide is being edited has to put what it wants on screen in its own content area, beside the stage rather than around it. The user leaves the child with Escape or the exit the framework draws, and the host hands the frame back.

Making a new block: every entry in the add-block menu is a template an editor's manifest declares, and the plugin makes every block from one, in BeuiApp::create_block, handed a Creation whose template() is the id the manifest gave it (Creation::MAIN, "main", for the plain block). A template may make a block of another type than its editor's - the presentation editor's slide templates make canvases - and names that type in the manifest so the host can offer it to a picker that only takes that type. The host opens an instance with no block, and create_block answers with the new block's id or with why it could not be made. creation.create(&content) makes the block with its first content and leaves it Detached, which is what it should stay as far as the plugin is concerned: the host adds the reference and sets the parent once it has the id, and then opens the block, so one plugin runtime serves the creation and the editor that follows it. The block and its content travel together in one CreateBlock, and the app's peer creates the block, seeds its first commit and only then sets the parent, so create_block does not have to wait for anything to arrive. content_file_creation::<C> is what the Creation component of a dialog template returns whose block is a file the user picks: it shows the file picker and creates the block from what the import function makes of the file. Beside the templates, the menu's "Import a file…" has the host pick any file and make a block of it with no editor involved, of the type whose module claims the file (guides/the_new_block_stack.md), so a type with a plain-file form can already be imported without a template.

Artifacts the editor generates: a block type that produces dynamic artifacts — a PNG exported from a drawing — lists ArtifactSettings among its regions, which is what tells the host this plugin answers for the artifacts its blocks make. The editor creates one with editor.blocks().create_artifact(&content, parent, name, artifact), whose be_block::Artifact points to the source block (a BlockRef, so the artifact is one of the source's backrefs), names its type, and carries the plugin's settings as an opaque payload (it is kept in the artifact's sealed metadata), and asks the host to open it. The host then keeps a second instance of the plugin open for as long as that artifact is on screen and asks it, through connect_artifact, describe_artifact and the ArtifactSettings component, and the Artifacts handle's source, on_regenerate and on_poll, what the settings currently produce, how to edit it inside the workspace's settings dialog (a Subregion of ArtifactSettings placed with dialog set: block-editor-beui puts the ArtifactSettings component inside a DialogBody with Cancel and Apply, Apply enabled once the copy differs from the stored settings, and the dialog answers through ChildState::dialog; committing that child applies it), and how to rebuild the artifact. The component draws only the settings, with no padding or title of its own. The host owns the settings it has stored and hands them over whenever they change; the settings screen edits a copy of them, which the host only stores once the user applies it, and throws away when the dialog is dismissed. Regeneration reads its source with host.content_of::<C>(source), a projection like any other, owned by the OwnedContentProjection it returns, that turns loaded once the host has sent it, and writes the result with host.replace_content(artifact, &content), so on_poll answers None until the source has arrived. The pixel art export and compiled logic are the examples.

A template whose block cannot exist until the user has chosen something (the file behind an image) sets "dialog": true and its editor also writes BeuiApp::Creation, one more component the framework builds a document of and shows as the picker's creation dialog. The plugin draws the dialog's whole inside, with no padding or title of the host's around it: the component is a styled DialogBody with its title ("New Foo"), its content and its actions, a Cancel and a Create whose on_click calls creation.accept() (disabled until the dialog is filled in, busy once pressed); the DialogBody's on_dismiss calls creation.cancel(). It says what the dialog makes with creation.on_create(...) rather than overriding create_block. The framework hands the DialogBody the host's narrow flag and bottom inset, and passes Escape, back and the host's dismissal (a press outside the dialog) to its on_dismiss, so the plugin decides what closing means; ContentFileCreation is the whole dialog for a block made from a picked file. The host fits the card or sheet to the height the dialog measures. Any other template is asked for its block as soon as the instance is open, and the host shows only a spinner while it starts.

3. Write the manifest

manifest.json is the plugin's single source of truth: the plugin reads its own identity out of it and the host reads everything else. Nothing in block-app is touched to add a plugin.

```json
{
  "id": "be3.foo",
  "name": "Foo",
  "version": "0.1.0",
  "editors": {
    "foo": {
      "id": "6f1c2e0a-93d4-4b7e-8a15-2c9e4f0b7d31",
      "edits": "00000000-0000-0000-0000-000000000000",
      "display_name": "Foo",
      "icon": "\ue3f4",
      "templates": {
        "main": {},
        "starter": {"name": "Starter foo", "icon": "\ue264", "category": "template"}
      },
      "regions": ["Frame"]
    }
  },
  "block_types": {
    "foo": {
      "id": "00000000-0000-0000-0000-000000000000",
      "display_name": "Foo",
      "icon": "\ue3f4",
      "color": [64, 155, 173],
      "module": "foo_types.wasm"
    }
  },
  "entry_point": "foo.wasm",
  "network": [],
  "extensions": []
}
```

editors maps a name, unique within the plugin and the one lib.rs pairs with an app, to each editor the plugin provides, with its own display name, icon, templates and the fields below. id is a uuid made fresh for that editor: it is what a view block (its VIEW_EDITOR metadata), a default editor setting and a template name the editor by, so it never changes and is never shared with another editor or a block type. edits is the CONTENT_TYPE of a block type that some plugin's manifest declares (its own, or another's: the counter's is Counter::CONTENT_TYPE) or that the host applies itself; the host refuses a plugin whose editor edits, or whose template makes, a type nobody declares. An editor that names no edits edits no block: it is part of the shell (the workspace, the desktop, Files, the add-block picker), run only where its role puts it, a session's view or the request its accepts names, so Open with, the default editors and the add-block menu never offer it, and the host refuses one that declares templates. display_name and icon name the editor, as Open with and the add-block menu show it; icon is a codepoint of the app's Lucide icon font, not a name to look up. Entry points name a file beside the manifest, which is where cargo already put the plugin, so nothing a plugin was compiled to is moved to be found.

block_types declares the block types the plugin brings, each under a name unique within the plugin (guides/adding_a_block.md, Declare it in the manifest): id, the CONTENT_TYPE; what a block of it is called (display_name), its icon and color; which of the host's structural edits it takes (children: add, delete and replace, each false unless named); press, Open or Zoom; exported_whole, whether exporting a child of a block of the type exports the block; and module, the plugin's type module, which every type of one plugin shares and the host runs once for the plugin. Every type names its module; a manifest without one is refused. These belong to the type, not to any editor of it, and the host's catalog of block types, which it sends plugins, is every installed manifest's block_types and the types the host applies itself (the settings types, the view, the repository and the checkout), whether or not an editor of the type is installed. The catalog carries the color to the add menu and file tree; templates use the color of the block type they create.
Labels retain the theme's text color. A block can override its file tree icon
and color independently through the defined metadata keys `metadata::ICON`
(a Lucide icon name, which `beui::icons::named` turns into its glyph) and
`metadata::ICON_COLOR` (an RGB byte triple). Blocks saved before the switch to
Lucide hold `metadata::MATERIAL_ICON`, a Material Symbols codepoint;
`BlockMetadata::icon` reads either, mapping the old picker's codepoints to their
Lucide names. Removing an override restores the block type default.

A block type may have several editors, in one plugin or across several. The first editor found that edits a block type is its built-in editor, which opens it anywhere nothing says otherwise; the others are offered beside it. edits "any" declares an editor for every block type, with no templates of its own: crates/editors/block-debug, the Debug view, is the example, and reads its block without knowing its type through editor.stored_head(block), a memo of the block's saved head (a StoredHead of the commit, the content type and the bytes, None before anything is saved, or the error that kept the host from reading it). The host reads those bytes from storage without going through any block type, and sends them again whenever the head moves (a head-watch the host answers), so the view shows what was last saved rather than live edits that have not been sealed yet. An editor with no edits shows no block's content: it is opened on its own view block, one whose VIEW_EDITOR metadata names it (workspace-ui, linux-desktop and the file tree are these, and be_block::profile names their ids), and a parent places it with ChildTarget::new(view, EditorViewContent::CONTENT_TYPE).edited_with(Some(editor)).viewed_by(view); it is never a type's built-in editor, and the host opens it on nothing but a block placed as its own view. The host lists every editor with what it edits in its catalog (Catalog::editors; BlockCatalog::editors_for, built_in_editor and editor on the plugin side). ChildTarget::edited_with(editor) asks the host to open a child in that editor rather than the built-in one, which replaces whatever editor the block was open in; a child that names none keeps whichever is open. open_block_with(id, block_type, editor) is open_block for a chosen editor, which reaches the workspace as ShowRequest::editor: the file tree's Open with sends it, and the workspace switches the block's tab to it, with a view block of its own, and remembers the choice with the tab. A tab with no choice opens in the default the person set in the Default editors settings (be_block::EditorSettings, edited by the settings plugin), or else the built-in editor. Only the workspace's tabs name an editor so far; every embedded child opens in the built-in one.

The entry point is the wasm module the build leaves beside the manifest: one artifact, the same bytes on the desktop, on Android and in the browser. network is the host names the plugin may reach through host.fetch, matched whole against the host of an https URL, and empty for a plugin that reaches nothing. extensions names the packages beside the core protocol the plugin uses, of those block_plugin_api::EXTENSIONS lists (only be3:linux-desktop so far): the host denies any call into one a plugin did not name, and the manifest is refused if it names one the host does not know.

templates is a map from an id, which only has to be unique within that editor, to how the add-block menu offers it; the menu offers them in the order they are written. category is important, regular (the default) or debug for the menu's main tab, which shows them in that order under the headings Common, More blocks and Debug, or template for its Templates tab, which groups them under the icon and display name of the editor that declares them. name and icon default to the editor's, block_type to the block type the editor edits (an editor of "any" or of nothing names its templates' block_type), and dialog to false. An editor with no templates is never offered: only another block ever produces one.

regions says which kinds of screen the host may give an instance: Frame, which every editor has and which is the whole rectangle it is edited in, Preview, and ArtifactSettings. accepts lists the requests a shell editor takes from the editors inside it - show_block, dialog, panel and window: the host hands a request an editor raises to the nearest editor around it, itself included, that accepts it, and the host's own requests to the outermost shell, which must accept them all. pick marks the editor the host runs picker children in (one per app). An ordinary editor accepts none. The optional fields default to the plainest answer: interaction says whether an embedded instance is live or only previewed until it is focused, capabilities carries rotation, aspect ratio, pan-and-zoom, max_zoom (how far past its fitted size the host lets a pan-and-zoom editor be zoomed, 32 unless it says otherwise - the map asks for far more, to reach street level) and pan (which gestures move the view, below), and resize says how an embedded instance may be resized.

The cursor the node under the pointer asks beui for is passed to the host, which shows it while the pointer is over that screen, so a canvas can offer a crosshair or a grabbing hand without knowing anything about the window it is in.

capabilities.pan_and_zoom means the editor's content has a view of its own rather than simply filling the space it is drawn in: the host works out where inside the editor's own content band the content goes, against the band the editor reported laying out last frame. The host owns that view. It hands the rectangle over as host.view(), in the coordinates the editor is drawing in, and the scale it is showing the content at as host.view_scale(), and the editor draws its content there at the resolution it is being shown at, keeping no zoom or offset of its own; an instance never told where its view is fills the content it is given instead, at a scale of one. The editor moves the view by asking - host.pan_view(delta) and host.zoom_view(factor, anchor) - which is what a zoom control in its toolbar calls (the pixel art editor puts a zoom readout and zoom buttons in its own). The host never fits the content: only the editor knows where it is, so a fit button is the editor's own zoom around its content's centre and pan of that centre to the middle of the view (guides/pan_and_zoom.md). The host answers against whatever it is showing the instance in, so those controls work the same in a tab of the editor's own as inside an infinite canvas the block sits in, where zooming zooms the canvas and the block's content grows with it; the editor cannot tell the difference, and its zoom readout is true either way as long as it reads it out of the view it was given: the rectangle for an editor holding a picture of a known size (the pixel art editor divides it by the image), the scale for one with a world of its own (the canvas draws a world unit that many pixels wide). Wheel, pinch and middle- or space-drag over the content belong to the host as well, so an editor leaves them alone - reading them only to know it should not start a gesture of its own, the way the pixel art editor holds off its tools while the view is being dragged - and the host reads them once, for the outermost view the pointer is over, so a wheel over a block being edited inside a canvas moves the canvas rather than both. capabilities.pan says which of those the host reads: TwoFinger, the default, is the wheel, a pinch or two-finger drag, and a middle- or space-drag; None is no gesture at all, leaving only the editor's own controls; OneFinger adds a plain drag or one finger, which only the editor can tell from a drag it means for itself, so its press goes to the editor, and an editor that finds it pressed on nothing of its own calls host.pan_drag_view() (beui: editor.pan_drag()). The host then cancels that pointer in the editor and moves the view with it until it lifts, with no round trip per move. The map pans on a press away from its points, the game board on a drag away from its pieces and the PDF editor on any press over its pages.

A beui editor declares capabilities.pan_and_zoom the same way and is answered the same way; it reads the view off the Editor it was handed and draws its content in a Canvas rather than working the rectangle out itself.

A manifest is untrusted input, so a bad one is skipped and reported in the Plugins debug window rather than crashing the app.

The host discovers plugins through plugins.json, the list of <plugin id>.plugin.json manifests the build stages beside the modules: beside the executable natively, in the APK's assets on Android, and at the bundle root in the browser. Native and Android share one loader (editors/plugin/discovery/bundle.rs) and differ only in how a file is read; the browser fetches the same files. Every platform runs the same host: plugin_host/runtime.rs owns the runtimes, the instances they show, input, errors and restarting, and a platform only implements its Backend - starting a runtime, exchanging be-ops frames with it, and handing over the frame it drew. There are two: plugin_host/wasm.rs runs the module under wasmtime on every platform but the browser, and plugin_host/web.rs runs the same module in a worker in the browser. Both are a `block_guest_host::Channel` under a `block_guest_host::Worker`, which queues frames, steps the guest once it is ready and finds a hung step; a Channel puts each event where `receive` finds it before it reads the worker's `waiting` flag to decide whether to wake the host (`block_guest_host::wakes`), since `Worker::queue` sets that flag before it polls and a step that carries frames keeps it set: either the poll finds the event or the guest's side sees the flag, and reading the flag first loses the wake for frames queued in between. So the host hears when every step it sent frames to ends, and `Worker::settled` turns true without polling; block-app counts type modules that are not settled as busy, so `settle` waits for their answers; the native one is block-guest-host's `thread::spawn`, the thread every wasmtime guest runs on. A plugin runs beside the app rather than inside it either way: a thread of its own under wasmtime, a worker of its own in the browser. A plugin that panics stops alone: block-guest-abi's panic hook hands the message and its place to the host through `be3_host.host_panic` (a guest's stderr does not reach the host), the runtime keeps it as the plugin's error, every region of it shows block-app's `CrashNotice` (surfaces/notices.rs) with a Reload button that restarts the runtime, and the host reports it as a toast (`notices::report`). A panic in the host's own code while it works for one plugin (inside `Runtime::contain`, which `poll`, `settle`, `with` and the other entry points in runtime.rs go through, and on the plugin's worker thread) stops that plugin the same way rather than the app. So do a wasm trap or the worker thread ending (the backend's error), a session that fails (a plugin that never says hello or never finishes shutting down, a call out of place), and a step the plugin has not finished within `STEP_TIMEOUT` (block-guest-host's worker.rs), which is how a plugin that hangs is found. However it stops, dropping its backend interrupts it (`Interrupter`, block-wasm-host's interrupt.rs): plugins are compiled with wasmtime's epoch interruption, so the guest traps at its next loop or call on every thread it started, and a thread blocked in `memory.atomic.wait` is woken to trap too; in the browser the worker is terminated, and its threads' workers with it. Every such stop goes through `Runtime::crashed`, which `take_crashed` hands to the app once, and the Plugins debug window's Crash button stops a plugin this way to try it. Neither side polls the other. Everything a plugin says arrives on its own, in the order it said it, and wakes the host; everything the host says reaches the plugin the same way.

4. Extending the protocol

If the editor needs something the host has and the plugin does not, add it to the `be3:plugin` WIT world in crates/block-plugin-api/wit (the rules for WIT and how each function travels are in guides/type_modules.md, "Operations and WIT", and crates/block-plugin-api/PROTOCOL.md lists the interfaces): its shapes beside the interface that uses them, something the plugin asks of the host in the import that fits (`host`, `blocks`, `shell` or `host-services`), and something the host asks of a plugin in plugin.wit, where `resource editor` is an open editor instance, so a call about one instance is a method of it. An import that needs an answer is an `async func`; a value the plugin follows is a resource whose `next: async func() -> T` the host answers with the latest change; a sync export is short and does no host IO. On the plugin's side, an export is served in crates/block-editor-plugin/src/wire.rs, which queues it as a `Delivery` the runtime takes in order (`Delivery::Editor` runs a closure on that instance's EditorSession), and an import is called straight from the code that needs it, such as EditorSession::outbound, under the editor's resource (`crate::asked::asking`); every runtime step runs inside the executor, so imports work anywhere in it. A value a task delivers outside a step, such as a watch's `next`, must wake the session's waker, or nothing asks for a frame while the app's clock is stopped. On the host's side, crates/block-app/src/plugin_host/wire.rs takes the generated `Call`s and calls the exports; what the runtime sends is an `Outbound` (calls.rs), what it hears a `Heard`, and a latest-value watch is `block_plugin_api::Watch`. A block id a call carries goes through the checkout's scope (`calls::BlockIds`, block_ids.rs). Anything the host and a plugin both draw — labels, shared painting helpers — belongs in crates/block-ui, which both depend on.

5. Work that does not finish in one frame

A plugin runtime draws only when the host asks it for a frame; it paces none of that itself. When the host tells it something that changes what it shows, or something wakes it, it says a frame is needed and waits, so a burst of input or view changes it cannot keep up with is drawn as one frame carrying all of it rather than one frame each. The frame it last drew says how long it wants to wait before being drawn again, which the host holds until it comes due and then answers with a single request in its own frame, so an editor animating without pause is drawn once per host frame instead of as fast as its process can run, and one the host is not drawing on screen is asked for nothing until it is on screen again. That request leaves as soon as the frame's input has been delivered (plugin_host::start_frames, run from beui's Document::on_interacted), before the host lays anything out, so the editor draws while the host lays out; it carries the frame's input - routed against where the editor sat and what covered it the last time it was drawn - and input the host routes always brings a request with it, since input is a change the editor will want to show. Once the host has laid out, it sends each runtime the size and place its regions were just given, asks for another frame where that changed what it shows, and waits for the answers before it paints (plugin_host::settle, run from beui's Document::on_laid_out), up to FRAME_BUDGET in plugin_host/runtime.rs; while a driven app's clock is stopped (guides/running/drive.md) it waits for every answer, up to STOPPED_CLOCK_FRAME_BUDGET, so how fast a loaded machine runs a plugin never changes which frame shows its answer. Everything the host sends that an editor lays out against - its screens' sizes, scales and frames, and its view - is followed by the plugin's configure export with a serial, and each frame the runtime commits (the answer to draw, a FrameCommit) names the last serial it had heard along with everything that frame laid out: region sizes, frame reports, window requests, child placements and occluders, and its pacing and presents (crates/block-editor-plugin's Screens::commit gathers them from the instances that ran). The host keeps the views and pixel densities it sent by serial (plugin_host/sent.rs) until a frame confirms a later one, and reads a frame's placements against the state at its serial rather than the one it has now. From those answers it takes only what draws the editor's frame (its texture, layout, frame-needed, paintings, and from a frame its reports, pacing and the child placements that only move the children it already has, since they say where its texture's children sit); the rest of a frame, such as children coming or going, region sizes and window requests, waits with the editor's other calls for the next frame's plugin_host::poll, which is where the browser takes in every answer, so host state changes at the same point on both. A child that has taken its parent's frame does not wait on the parent's answer to learn where the camera put it: the parent marks the children that follow its view, the host moves each from the view it had sent at the parent's frame's serial to its own current camera, works the child's view out from that, and asks both editors in the same frame (guides/pan_and_zoom.md). An editor that answers in time is shown in the frame that asked; one that runs over is shown in a later frame without holding the host up any longer, and until then its last painting is drawn at the size it was painted, from the region's top-left corner, cropped to the region or short of it at the right and bottom, never stretched over it, on every platform (native crops the texture, the browser places the canvas the same way, both through `unstretched` in plugin_host/presenter.rs); its children and input method area stay where that painting put them. The browser cannot block on a worker, so there the answer always lands in a later frame. A call that changes nothing it draws costs no frame, and a frame runs only the instances a call or a wake touched, the ones that asked to be drawn again, and all of them when the layout moves, so an idle instance beside a busy one costs nothing either. The host repaints on the same rule: a call that changes nothing it draws does not schedule a frame, and nothing about a plugin is polled. An editor doing work off the frame — the PDF editor renders its pages on a thread of its own — asks to be drawn again through ui.ctx().request_repaint() or request_repaint_after(...), which reaches the runtime's loop wherever the request came from; block_editor_beui::Waker, which host.waker() hands out, does the same for work that has no ui to ask from. An idle editor that asks for nothing costs nothing.

A plugin that links C calling setjmp - FreeType, which beui shapes and rasterizes glyphs with - is compiled with the SjLj lowering the WASI sysroot's setjmp needs, which turns those calls into the wasm exception-handling instructions. The host runs plugins with that proposal on, so nothing about it is the plugin's business, but a module carrying a tag section is a module only a runtime with exception handling can load: `./scripts/buck run //crates/block-wasm-host:example-instantiate` is what says whether one does.

A plugin is one wasm for every platform, so a dependency it cannot have there is a dependency it cannot have at all: nothing that reaches the network (host.fetch instead), nothing that opens a file, and nothing wasm-bindgen. It is linked against the plugin SDK, which holds everything the plugins have in common (guides/plugin_sdk.md), so its module holds only what is its own. A C or C++ library links into the plugin's wasm as a static library for wasm32-wasip1-threads, named in `editor(extra_deps = [...])`, and has to be compiled position-independent to be linked into one, which the plugins' toolchain does; the PDF editor links PDFium, which third-party/pdfium builds from source with it (guides/plugin_sdk.md). std::thread works — the host implements thread spawning against the plugin's own shared memory — but only the plugin's first thread may talk to the GPU, and a call from any other is refused by name.

6. Build scripts

Nothing to edit but the editor's BUCK file, which is one `editor()` call naming the module the manifest's entry_point names and, as `types`, the types crate's `:module` (crates/editors/checklist/BUCK is the pattern), which the app stages beside the plugin under the name its block_types give it, with its .cwasm and its SHA-256, the tag of its sessions (buck/app/stage.sh). Every crate directly under crates/editors is staged as a plugin (a types crate under it belongs to its plugin): `./scripts/buck run //crates/block-app:native` builds each one for wasm32-wasip1-threads with the plugin profile - its own configuration, because the app links wgpu with real backends while a guest links it with only the custom one - and lays it out beside the app with its manifest renamed <plugin id>.plugin.json, and compiles it to foo.cwasm, which opening the editor maps in rather than waiting seconds for Cranelift. The app reads foo.wasm and compiles it itself whenever the artifact is missing or was made by a different wasmtime or engine configuration (`configuration()` in block-wasm-host, which the precompiler and the host share, so epoch interruption is in both; the precompiler picks a plugin's or a pure guest's configuration by which one validates the module), which is how a cross-compiled build runs. `//crates/block-app:plugins` is the plugins alone. guides/buck2.md has the rest.

7. Verification

./scripts/verify lints every editor as the wasm guest it ships as and runs its tests there. ./scripts/buck build //crates/block-app:web builds the browser's half of the bootstrap and every plugin as the guest it actually ships as. A plugin can be driven without a GUI: ./scripts/buck run //crates/block-wasm-host:example-instantiate -- PLUGIN.wasm EDITOR_ID takes a plugin built by //crates/editors/foo:module through the handshake, opens an instance of the editor with that manifest id, asks for a frame and fails unless it presented a surface; the plugin SDK module (//crates/block-plugin-sdk:module) must lie beside it under the file name the plugin's identity names, as the app stages them.

An editor that draws with the GPU rather than with beui's own shapes uses a beui `Drawing` node painting a gpu Drawing through `draw_gpu` (guides/beui.md): the gpu work sits behind a Draw the beui renderer runs while it paints, and a headless test, which builds no renderer, never opens a device. A snapshot never holds what it drew, so a test of one asserts on the block and on what the editor paints around it.

A plugin never learns where its pixels live. It asks for a render target and is handed an opaque texture, which under wasmtime is a texture the app already owns in its own device — nothing is exported or imported — and in the browser is a texture on a device the plugin's worker owns. The worker draws each place the host shows the plugin into a canvas the page transferred to it, and the page keeps those canvases behind the app, which leaves a transparent hole wherever one shows through, so what a plugin draws never leaves the worker's GPU. Its wgpu calls reach that device over the `be3:gpu` WIT world in crates/block-gpu-abi/wit (guides/plugin_sdk.md, "The gpu"), generated once for every side: block-gpu-guest builds wgpu's custom backend on its guest bindings, block-gpu-host's `Gpu` implements its `Host` trait, and the generated glue is what wasmtime links directly and the browser exports from crates/block-gpu-shim, a wasm-bindgen module the worker instantiates first, binds the plugin's imports to, and hands the plugin's memory to read pointers from.

The workspace's History tab lists saved revisions of the active file. `EditorHost::list_revisions`,
`preview_revision`, and `restore_revision` are asks like any other (Asking the host, above). A preview is a temporary block id for a separate, read-only editor; release it
with `release_revision`. The host isolates its content from live updates and rejects mutation
requests from it and its nested editors. Nested blocks show their current contents. Restoring
seals current edits and publishes the selected file content as a new revision, preserving current
metadata and leaving other blocks unchanged. This uses existing commits and retention, separate
from the per-peer undo stack.
