Every editor in the app is a plugin, and so is the app's own window: block-app signs the user in, hosts plugins, draws the status bar along the bottom with the More menu in it, and owns the dialogs a plugin cannot draw for itself. Everything above that bar - the tabs, the pane of files, the block's status bar - is crates/editors/workspace_ui, an ordinary plugin on an empty block type that the app resolves through the root settings block the way it resolves any other setting, creating it the first time a workspace is opened. It places the file tree and the block each tab is showing as children of its own, each owning a frame of its own (see below), so every editor on the screen is a plugin instance the app is only compositing. The only editor block-app has left is the placeholder for a block type no plugin claims. This is how one is added.

1. Add the block (if the block type is new)

- crates/be-block/src/foo.rs — the content as #[derive(Model)] structs, impl Root with a fresh CONTENT_TYPE uuid, pub type FooContent = Document<Foo>, and the edits an editor makes as helpers returning be_model::Edit. guides/adding_a_block.md says how.
- crates/be-block/src/lib.rs — declare the module and re-export Foo and FooContent.
- crates/block-app/src/be.rs — add kind_with_history::<be_block::FooContent>() to KINDS (kind::<C>() for a type without undo). This is the one place outside the plugin that learns about a new type.
- crates/be-block/src/tests/ — one file per test (edits, references, merge, undo).
- A block holds what it is, not what an editor makes of it. The image block keeps the file's bytes and a header saying what decoding them found — or why it failed — which the editor fills in through an operation the first time it draws the image. Nothing but the plugin then needs a decoder, and no other client has to decode the block to know its shape.

2. Create the plugin package

- crates/editors/foo/Cargo.toml — copy checklist's: crate-type = ["cdylib", "rlib"], deps block-editor-plugin, beui (default-features = false, features = ["render"]) and uuid, and block-ui-test as a dev-dependency. block_editor_plugin re-exports be_block, so the editor names its content type without depending on be-block itself. The package name is the wasm artifact stem, so a multi-word editor uses underscores (workspace_index). It also has to be a name no crate the workspace depends on already has, so the image editor's package is image_block; the display name in the manifest is what the user sees.
- crates/editors/foo/src/lib.rs — block_editor_plugin::beui_plugin!(app::FooApp, "../manifest.json");. A plugin may edit several related block types (the logic plugin in crates/editors/logic_grid edits logic grids, logic games, hotbars and compiled logic): each is one BeuiApp, and lib.rs names them by content type instead - beui_plugin!("../manifest.json", { LogicGridContent => app::LogicGridApp, HotbarContent => hotbar::app::HotbarApp, ... }). The framework opens each instance with the app of the block type the host names, and refuses to start unless the apps cover exactly the editors the manifest declares. Related editors belong in one plugin rather than one each: they share a module, and the host runs one runtime for them.
- crates/editors/foo/src/app.rs — impl block_editor_plugin::BeuiApp. An editor has no state struct and no connect: it is one #[component] function handed an Editor, and the type it names in beui_plugin! only carries that function and the two or three answers the host asks of the editor as a whole. What it wants of its block it takes as editor.block_content::<FooContent>(), a ContentProjection the framework pumps at the top of every frame inside the document's reactive scope: it registers what the view reads as projections of the content - project, or field, ids and object for one field, one list's order or one object - and writes back through operate with the edits the content type's helpers build, which is already held behind whether the host says the block is editable, so a change to the block wakes the bindings that read what changed rather than rebuilding the view. Another block's content is editor.content_of::<C>(block), the same projection keyed by that block. guides/reactive.md says how. Local-only view state is a signal the component makes, and work that is neither - a snapshot to recompute, a picker's answer to collect - is an effect over the signals it reads: nothing in an editor runs every frame. What the host says arrives as signals on the Editor at the top of the frame it was delivered for - editor.replies() and editor.on_reply(...) when a request is answered, editor.drag() and editor.files() for drops, editor.audio(), editor.history(block), editor.focused_block(), editor.web_view_events() and editor.peers::<P>() for the rest - and projections and graph reads track, so an effect or memo that reads them runs again when they change. Something that genuinely moves with time, like playback, is a beui create_timer that stops once it has nothing left to do, and work finishing on another thread wakes the editor through the Waker from editor.woken(), whose signal an effect reads to collect the result. Whether the host says the block is editable is editor.editable(), a signal written before every frame, and editor.read_only() is the memo a disabled prop takes. A link to another block is <BlockLink editor block>, handed the Editor and an Option<ChildTarget>: it follows that block's name and icon and opens it in the host when it is clicked. Icons come from beui::icons, drawn with the Material Symbols font every beui context carries.
- crates/editors/foo/manifest.json — the plugin's identity and everything the host is told about it (see below).
- Root Cargo.toml — add "crates/editors/foo" to members.

Editors draw with crates/beui, the project's own retained-mode ui. The plugin system is events in and pixels out - the host sends the input it routed and the plugin hands back the surface it drew - and beui is only what the framework puts in between. The framework keeps a beui Context per screen the instance is given, turns the host's own InputEvents into beui's, builds BeuiApp::view(editor) once and keeps the Document it produced, shows that document in the region it was given, and paints what the frame produced with beui's own wgpu renderer straight into the surface the host composites, one render pass per screen scissored to where that screen sits. Colours are written the way the surface wants them: the plugin surface is not an sRGB format, so beui encodes gamma there and linear where it draws its own window.

A plugin may open no font file, so the framework builds each beui context with beui::Context::new(), over the fonts beui compiles in (FontSources::default()), which is also what makes a beui editor paint the same on the desktop, on Android and in the browser.

What an editor gets is the whole frame. The framework draws a top bar across it whenever the host asks for one (FrameSpec::top_bar): undo and redo, the block's name as a field that looks like plain text until it is hovered or focused - empty with the derived name as its placeholder until someone names the block, and clearing it gives the derived name back - and Share, plus a Close button when the frame belongs to a child that took it over, which Escape also leaves. The bar owns Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y for the block while it is shown, except when the focus is in something that takes text, which keeps its own undo. A dialog creation instance gets the dialog's whole plugin rectangle through creation_frame, and an editor that declares the Preview region writes one more #[component] function, BeuiApp::preview_view, which the framework builds a second document of - with a second Editor of its own, so the two regions place their children apart - the first time the host asks for that region. The counter editor is the smallest example, checklist shows a larger retained document, the deterministic game shows dialog creation with a host block picker, and the presentation editor shows children, playback and a preview.

An editor draws its own chrome inside that frame rather than being called back for one band at a time. What it is told instead is whether the host is showing this instance's chrome at all this frame - editor.chrome_shown(), a signal the framework writes before every frame - and an editor with a sidebar of its own hides it when that reads false, which is what keeps the same code right for a tab of its own and for a block being edited live inside a canvas. Because the host cannot see where an editor put that sidebar, the editor names the node its content is in once, with editor.content(&node_ref), and the framework reports that node's rectangle after every layout; that rectangle is the one the host pans, zooms and reads wheel gestures against, so a wheel over the sidebar is not a wheel over the content. The band itself is <Sidebar shown={editor.chrome_shown()}>, a block_editor_plugin component the editors share: it takes the side it sits on, scrolls what is written between its tags, draws the border against the content, and measures to nothing while shown is false, so the row it is written in gives the whole frame back to the content. The database, worktree, game module and audio editors are the examples.

An editor whose layout is a dock of tabs - the workspace is the one that does this - builds it with block_editor_plugin::EditorDock rather than beui's DockArea. It takes the same props (state, title, closable, on_change, on_close and the content builder) plus the editor. When the host offers panes (editor.host().panes_offered(), which the app does), the dock draws nothing inside the frame: the editor session describes the dock's tabs and their layout to the host as panes, builds each tab in a beui document of its own, and draws it into that tab's pane region, a screen of its own the host places wherever the tab is. The app shows those panes as a pinned tab group in its own dock, so a person can split them, group them or pop one out into a window like any tab of the app, and only the plugin's own panes can go back into the group. What the person does comes back as the dock's on_change - the layout the plugin's panes are left in, without any that were moved out of the group - and on_close, and the plugin keeps building a pane that was moved out until it is closed. editor.show_pane(tab) asks the host to bring one to the front wherever it is. A host that does not offer panes, which is what a plugin's own tests run against, gets an ordinary DockArea. The frame is still where the editor's own logic runs, so the app keeps drawing it off screen, one pixel tall; anything that must be seen belongs in a pane. Each pane's document is its own reactive zone (see guides/reactive.md), so a signal a pane reads may be written from any of the editor's documents.

The view itself arrives in beui's own coordinates as signals on the Editor the component was handed: editor.canvas() for the beui::reactive::CanvasView a Canvas takes and editor.scale() for what the content is being shown at, both written before every frame, with editor.pan, zoom, fit and reveal - which pans a rectangle of the editor's own world into the middle of the content - to ask the host to move it. The host still owns it, so those work the same in a tab and inside an infinite canvas. beui's Canvas is what puts the content where the view says: its CanvasItem children carry a rectangle in the editor's own world coordinates, and the canvas maps each one through the view, clipping and culling to the rectangle it was laid out at. A canvas never told where its view is fills the space it was given at a scale of one, and one given a width and a height reports that as its size, which is what lets a canvas of absolutely placed items sit inside a Scroll. Placing an item is not transforming it, so text inside one keeps whatever size it asks for: an editor whose content should grow with the zoom reads the scale and sizes its own text by it. The pan and zoom editor is the smallest example of all of this, and its block stores nothing at all.

Testing one is block_ui_test::BeuiTest: it is built from an Editor, or from a Creation for a dialog, and block_ui_test::ContentHarness stands in for the host around it, holding the content of the editor's block and of any block it watches and applying what the editor sends; so a test holds the same handle the component was handed and reads the content rectangle and the view requests back off it. It drives the app with beui events (click_at, key_press, text) at the rectangles beui laid its nodes out at (Document::node_rect). Its snapshot is what beui's renderer would hand the gpu for that frame (beui::quads): the rounded rectangles and glyphs it turns into instances, each glyph carrying its own coverage image rather than a place in the atlas. No gpu draws it, so no driver can change it. guides/testing_a_gui.md says how they are run.

A plugin has no connection, no block store and no key of its own: the app is the only peer, and a plugin reaches blocks only through the host. Content arrives as the ContentProjections above. The graph - which blocks exist, their names, parents, references and access - is the host's mirror of the server's, and a plugin asks about it with editor.watch_blocks(query), a memo of the BlockInfos the host answers a BlockQuery with (Roots, Detached, Children, References, Backrefs, Parents or one Block), and changes it through editor.blocks(), a Blocks handle: create, create_named, create_artifact and create_with make a block with its first content, set_parent moves one, set_name names one by hand, info and access read what the host last said, and watch is the query as a BlockList without the memo. editor.create_child(&content) is create under the editor's own block. Each of these is a GraphCommand the session sends the host as CreateBlock, SetParent or SetName; the host applies it to its mirror straight away, checks the account may edit what it touches, and hands it to the app's peer, which carries it to the server. Because the peer belongs to the app rather than to the instance, a block an instance has just created still reaches the server after that instance closes.

What the EditorHost (editor.host()) offers, for anything the plugin cannot do itself:

- open_block(id, block_type) — opens another block in a tab of its own.
- block_types() — the host's registered block types, for naming and illustrating a block this editor only holds a reference to. Pass it to block_ui::BlockLabel (re-exported as block_editor_plugin::block_ui) so labels match the rest of the app, including how an automatic name is italicized.
- editable() — whether the block this instance was opened on may be edited, so an editor does not write back what it worked out (an image's decoded size) on behalf of a reader. The host cannot disable a plugin's own surface the way it greys out an editor it draws itself, so an editor whose block may only be read keeps every gesture that would change it behind this: the pixel art editor still pans, zooms and reads out pixels, but draws nothing and disables the buttons that would.
- drag() — the block the app is dragging over the screen being drawn, in that screen's own coordinates, and whether it has been let go. Draw the drop feedback yourself and answer accept_drag(bool), which decides the cursor the host shows. A drag that starts and ends inside the editor's own document - a card between columns, a slot in a hotbar - never reaches the host: that is beui's Draggable and DropTarget (guides/beui.md).
- pick_file(filter) — the host's own file picker, the only one that works on desktop, Android and the browser alike. block_editor_plugin::FilePicker wraps it the way the app's own picker works: open(&host, filter), is_open(), and poll(&host) from editor.on_reply(...) to take the answer once the host has sent it.
- fetch(url) — a GET the host makes on the plugin's behalf, answered with take_fetch(request) once the body arrives or the attempt fails. A plugin has no network of its own on any platform, so this is the only way it reaches one, and the host refuses any URL whose host name the manifest's network list does not name. The paint review editor downloads its snapshots this way.
- pick_block(filter) — the host's own block picker, which is how an editor acquires a child without waiting for one to be dragged in. The filter names what is being chosen, the block types that may be chosen, empty for any, and whether the picker opens on the templates the host offers rather than on its new-block grid. block_editor_plugin::BlockPicker wraps it the same way FilePicker wraps the file one, and answers with the block the user chose or created. A creation dialog may ask for one too, which is how an editor whose block cannot be made until it references another one - the game editor, which plays a game module block - gets that block before its own exists; the host opens the picker over the dialog it is already showing, and a block created there is created at the root.
- present(on) and presenting() — asks the host to give this instance the whole window with no chrome bands and show nothing else of the app, and reports what the host settled on. The host owns the answer: it takes presenting away when the user presses Escape or the instance stops being the one on screen, so an editor reads presenting() rather than remembering what it asked for, and draws its content the same way either way.
- open_web_view(url), place_web_view(rect), load_web_view(url), reload_web_view(), focus_app(), close_web_view() and take_web_view_events() — a web view of the operating system's own, laid over the app where the editor says, which is the only browser a plugin has. The editor opens it once, says each frame where it goes inside its own screen — None while it has nothing to show — and reads back what the page did: the browser tab editor turns those events into the history its block keeps. The host hides the view while the instance is not being drawn and closes it with the instance, and answers a platform with no embedded browser with a failure the editor shows in its place.
- grab_cursor(on) and cursor_grabbed() — asks the host to hold the pointer still and hide it, which is what an editor that looks around a scene wants: while it is held the editor reads beui's PointerMotion events rather than a position; a beui context that locks the pointer (Context::set_pointer_locked) asks for it on the editor's behalf. The host holds it while any instance asks and lets go as soon as none does, so an instance that closes or stops being drawn cannot leave the pointer trapped; the editor still lets go itself on Escape or when it loses focus. A beui editor does not ask the host itself: it writes unstyled::PointerLock (guides/beui.md) and the framework does the asking, calling grab_cursor for whichever of the instance's screens says it is holding the pointer and turning the host's PointerMotion and Focus events into beui's, so the control reads motion rather than a position and lets go on Escape or a lost focus without knowing there is a host at all. The scene_3d editor is the example.
- occlude(rect) — declares that the editor draws over that rectangle after the children placed so far, so the host neither draws nor routes input to them there.
- set_creation_ready(bool) — whether a creation dialog has been filled in, which is what lets the user accept it (see below).
- take_show_requests(), report_focus(focused), watch_artifacts(blocks), artifact(block), regenerate_artifact/edit_artifact/unlink_artifact(block), simulate_access(block, level), close_editor(block) — what the instance that draws the window needs and no other editor has any use for. The host hands that instance every block anything asks to open, including the blocks it asks for itself, so opening a block is one path however it started; it answers with the block the user is looking at, which the host then tells every other instance; it names the blocks whose dynamic artifacts it is showing and reads back what the host's own artifact instances describe; and it asks the host for the things only the host can do to a block it is not itself drawing - holding it to less access than the account has, and closing the editor of a tab that was closed.

What the host asks of an editor, beyond drawing, it asks through its `Editor`. `presence_visible()` is a signal the framework writes before every frame saying whether anyone is looking at this block, which is when a collaborative cursor is worth publishing, and `revealed()` asks it to scroll one of those cursors into view - only the editor knows where in its content that is. The cursor itself goes through editor.show(Some(&value)), with a value of a be_block::presence::PresenceKind, and editor.peers::<P>() is a signal of every other peer's value of that kind; host.show_presence is the same for a block other than the editor's own. The host carries it to the app's peer, which shares it with the block's session and never saves it, and takes it away when the instance closes. The framework shows a UserActive entry of its own while the block is visible, and a peer never sees what it showed itself, so the presence an editor reads is only ever other people's - never a cursor for the person at the keyboard. A cursor carries its own colour, picked with pick_free_color against the colours the other peers are showing. `on_replace_child(...)` registers the answer to a block the host copied because it was being edited in two places at once; an editor whose references live inside its own content (the text editor's block URLs) rewrites them and answers true, and one that leaves it to the block's own structural edit answers false. That callback is made outside the document's reactive scope, so it edits the block and leaves the view to catch up on the next frame rather than writing signals. beui has no IME output of its own yet, so an editor cannot report an IME area.

An editor never draws the top bar or the way out of its own frame. The framework draws both itself, so an editor cannot lose them. Which chrome an instance is given changes from frame to frame: the same code draws a tab of its own, a block being edited inside a canvas, and a slide inside a deck, and editor.chrome_shown() is how it tells them apart.

BeuiApp::intrinsic_size, or editor.set_intrinsic_size for one that changes, reports the size the editor wants wherever the host embeds it (a canvas, a text block). BeuiApp::aspect_ratio reports the shape of the block, which the host holds a preview to. Leave either unimplemented to take the host's default.

Drawing the block itself: an editor that lists Preview among its regions is asked to draw its block wherever the host paints it rather than opening it — a canvas entity, a slide, a block embedded in text. The host maps that screen onto the quad it is painting, straight from the plugin's surface, so preview_view fills the screen it is given and lets the host place, rotate and fade it. It has no background of its own, so whatever is behind the block shows through. A frame is the same: it is transparent wherever the editor does not paint, which is what lets the layer beneath show through around a block being edited inside a canvas. Children placed in a preview work like children anywhere else, so an editor whose block is only its children - a presentation showing its first slide - draws them there as previews.

Embedding other editors: the <ChildBlock> component puts another block's editor inside this one — another plugin, several levels deep. Every editor is a plugin, so a child is always another one of these. It takes the Editor it was handed, a block prop naming the block and its type (None while the reference has not resolved yet), the mode and layer the placement wants, and own_frame for a child that lays its own chrome out inside the rectangle. It reserves the space it is laid out in with beui's Embed base node, which reports the rectangle and the clip it was laid out in, and the framework turns that into a placement, one per frame, in the region being drawn. The subtree written between its tags is drawn inside that rectangle and is handed a ChildBlockHandle carrying a ReadSignal<ChildState> - placed, available, hovered, active, intrinsic_size, aspect_ratio, interaction, capabilities, resize and error - so a placeholder is a Frame whose visibility follows that signal rather than a branch in the view; on_state reports the same value to the editor around it, which is how a stage sizes itself to the slide's aspect ratio, and Frame's aspect_ratio prop is what fits a child of a known shape into the space a stage was given.

A child is drawn *under* the plugin's own surface and the space it takes is cut out of it, so anything the editor draws after the child — a selection handle, a drag ghost, a menu, a modal — covers it simply by being drawn later. A child that is genuinely translucent cannot composite that way and is placed with layer=ChildLayer::Above instead, which composites against the plugin's pixels and cannot be drawn over.

A child placed with own_frame=true lays its own chrome out inside the rectangle it was placed at instead: it draws its toolbar row and sidebars there, and the editor that placed it keeps its whole frame and every band in it. Placed with top_bar=true as well, it gets the framework's top bar over that rectangle, which is how every block tab in the workspace gets one while the pane of files does not. That is the other way to run an editor inside one - ChildMode::Live hands the frame over, own_frame gives the child one of its own - and it is what lets the workspace plugin put a pane of files beside the block being edited, each with its own toolbar over its own part of the window.

The editor keeps every click over a passive child: nothing is delivered to the child until the editor promotes it to ChildMode::Active, which is what a double-click or an Edit button does, and the host takes the promotion away again when the user clicks outside or presses Escape. A child that is not something the user promoted but the whole of what the editor shows - the slide a presentation is editing - is placed with ChildMode::Live instead, which is live from the moment it is placed and which the host never takes away. ChildMode::Preview asks for the other end of that: the host draws the block rather than running its editor, which is what a filmstrip of thumbnails wants. A preview child is composited over the plugin like any other child below it: the host draws the block's own preview into the hole, clipped to where the child was placed. None of that is the editor's to arrange: place the child, ask for Preview, and draw the rest around it. ChildState is what the host made of the child: available is false when the block cannot be opened — a block already open above this editor is refused, and error says so — while intrinsic_size, aspect_ratio, hovered, active, interaction, capabilities and resize are what the host last saw. interaction is the child's own manifest answer, which is how an editor knows whether to run the child live or to draw it as a preview until the user asks to edit it; capabilities and resize are what an editor laying children out in a world of its own needs to know before it draws a resize handle. Tell the child what you gave it with the intrinsic prop, which reaches it as the size it was resized to, and place a preview child at an angle or faded with the rotation and opacity props. A child with a view of its own hands its pan, zoom and fit requests back through on_view_change rather than moving itself, so the editor that placed it decides what they mean - a canvas turns a block asking to fit into fitting that block in the canvas. Place only the children that are visible: the host runs a bounded number of them as editors and draws the rest as previews.

A child the user has promoted to ChildMode::Active, or one the editor placed with ChildMode::Live, takes the frame over: it is handed the same frame this instance was, draws every chrome band in it, and draws its content at the rectangle it was placed at. The editor that placed it draws no chrome at all while that lasts: its bands go away and its content takes the whole frame rather than keeping a band of nothing where its toolbar was, so a canvas shows more of its world there. Its camera is untouched by that, so the world - and the child's own rectangle in it - stays exactly where it was on screen. The part of the frame the child paints its chrome over is withheld from the editor underneath, so a click on the child's toolbar or its sidebar belongs to the child; a click on the rest of the frame, which the child leaves transparent, falls through to the editor that placed it, and that is what takes the frame back. There is no way to nest a child's chrome inside a band of your own, and no way to keep a band while a child has the frame - a deck whose slide is being edited has to put what it wants on screen in its own content area, beside the stage rather than around it. The user leaves the child with Escape or the exit the framework draws, and the host hands the frame back.

Making a new block: every entry in the add-block menu is a template an editor's manifest declares, and the plugin makes every block from one, in BeuiApp::create_block, handed a Creation whose template() is the id the manifest gave it (Creation::MAIN, "main", for the plain block). A template may make a block of another type than its editor's - the presentation editor's slide templates make canvases - and names that type in the manifest so the host can offer it to a picker that only takes that type. The host opens an instance with no block, and create_block answers with the new block's id or with why it could not be made. creation.create(&content) makes the block with its first content and leaves it Detached, which is what it should stay as far as the plugin is concerned: the host adds the reference and sets the parent once it has the id, and then opens the block, so one plugin runtime serves the creation and the editor that follows it. The block and its content travel together in one CreateBlock, and the app's peer creates the block, seeds its first commit and only then sets the parent, so create_block does not have to wait for anything to arrive. content_file_creation::<C> is the creation_view of a dialog template whose block is a file the user picks: it shows the file picker and creates the block from what the import function makes of the file.

Artifacts the editor generates: a block type that produces dynamic artifacts — a PNG exported from a drawing — lists ArtifactSettings among its regions, which is what tells the host this plugin answers for the artifacts its blocks make. The editor creates one with editor.blocks().create_artifact(&content, parent, name, source), whose ArtifactSource names the source's type and carries whatever the plugin needs as an opaque payload (it is kept in the artifact's sealed metadata), and asks the host to open it. The host then keeps a second instance of the plugin open for as long as that artifact is on screen and asks it, through connect_artifact, describe_artifact and artifact_settings_view, and the Artifacts handle's on_regenerate and on_poll, which block the payload was generated from and what it currently produces, how to edit it inside the host's settings dialog, and how to rebuild the artifact. The host owns the settings it has stored and hands them over whenever they change; the settings screen edits a copy of them, which the host only stores once the user applies it, and throws away when the dialog is dismissed. Regeneration reads its source with host.content_of::<C>(source), a projection like any other that turns loaded once the host has sent it, and writes the result with host.replace_content(artifact, &content), so on_poll answers None until the source has arrived. The pixel art export and compiled logic are the examples.

A template whose block cannot exist until the user has chosen something (the file behind an image) sets "dialog": true and its editor also writes creation_view, one more #[component] function the framework builds a document of and draws inside the host's shared dialog frame. It says what the dialog makes with creation.on_create(...) rather than overriding create_block, and answers creation.set_ready(true) once it has been filled in, which tells the host the dialog may be accepted. Any other template is asked for its block as soon as the instance is open, and the host shows only a spinner while it starts.

3. Write the manifest

manifest.json is the plugin's single source of truth: the plugin reads its own identity out of it and the host reads everything else. Nothing in block-app is touched to add a plugin.

```json
{
  "id": "be3.foo",
  "name": "Foo",
  "version": "0.1.0",
  "editors": [
    {
      "block_type": "00000000-0000-0000-0000-000000000000",
      "display_name": "Foo",
      "icon": "\ue3f4",
      "templates": {
        "main": {},
        "starter": {"name": "Starter foo", "icon": "\ue264", "category": "template"}
      },
      "regions": ["Frame"],
      "chrome": ["Toolbar"]
    }
  ],
  "entry_point": "foo.wasm",
  "network": []
}
```

editors lists every block type the plugin edits, each with its own display name, icon, templates and the fields below. block_type is the CONTENT_TYPE of a be-block Root (the counter's is Counter::CONTENT_TYPE) that the app registers in KINDS — a plugin cannot bring a block type of its own, which is what keeps child edits, undo and duplication working. icon is a codepoint of the app's Material font, not a name to look up. Entry points name a file beside the manifest, which is where cargo already put the plugin, so nothing a plugin was compiled to is moved to be found.

The entry point is the wasm module the build leaves beside the manifest: one artifact, the same bytes on the desktop, on Android and in the browser. network is the host names the plugin may reach through host.fetch, matched whole against the host of an https URL, and empty for a plugin that reaches nothing.

templates is a map from an id, which only has to be unique within that editor, to how the add-block menu offers it; the menu offers them in the order they are written. category is important, regular (the default) or debug for the menu's main tab, which shows them in that order under the headings Common, More blocks and Debug, or template for its Templates tab, which groups them under the icon and display name of the editor that declares them. name and icon default to the editor's, block_type to the editor's block type, and dialog to false. An editor with no templates is never offered: only another block ever produces one.

regions says which kinds of screen the host may give an instance: Frame, which every editor has and which is the whole rectangle it is edited in, Preview, and ArtifactSettings. chrome says which of the toolbar row and the two sidebars this editor offers inside its frame; the plugin reads that list out of its own manifest and the framework calls only the bands it names. The optional fields default to the plainest answer: children says which of the host's structural edits the block type accepts, interaction says whether an embedded instance is live or only previewed until it is focused, capabilities carries rotation, aspect ratio and pan-and-zoom, and resize says how an embedded instance may be resized.

The cursor the node under the pointer asks beui for is passed to the host, which shows it while the pointer is over that screen, so a canvas can offer a crosshair or a grabbing hand without knowing anything about the window it is in.

capabilities.pan_and_zoom means the editor's content has a view of its own rather than simply filling the space it is drawn in: the host works out where inside the editor's own content band the content goes, against the band the editor reported laying out last frame. The host owns that view. It hands the rectangle over as host.view(), in the coordinates the editor is drawing in, and the scale it is showing the content at as host.view_scale(), and the editor draws its content there at the resolution it is being shown at, keeping no zoom or offset of its own; an instance never told where its view is fills the content it is given instead, at a scale of one. The editor moves the view by asking - host.pan_view(delta), host.zoom_view(factor, anchor) and host.fit_view() - which is what a zoom or fit control in its toolbar calls (the pixel art editor puts a zoom readout, zoom buttons and a fit button in its own). The host answers against whatever it is showing the instance in, so those controls work the same in a tab of the editor's own as inside an infinite canvas the block sits in, where zooming zooms the canvas and the block's content grows with it; the editor cannot tell the difference, and its zoom readout is true either way as long as it reads it out of the view it was given: the rectangle for an editor holding a picture of a known size (the pixel art editor divides it by the image), the scale for one with a world of its own (the canvas draws a world unit that many pixels wide). Wheel, pinch and middle- or space-drag over the content belong to the host as well, so an editor leaves them alone - reading them only to know it should not start a gesture of its own, the way the pixel art editor holds off its tools while the view is being dragged - and the host reads them once, for the outermost view the pointer is over, so a wheel over a block being edited inside a canvas moves the canvas rather than both. A gesture only that editor knows about - the PDF editor panning on a plain drag - it turns into a request of its own.

A beui editor declares capabilities.pan_and_zoom the same way and is answered the same way; it reads the view off the Editor it was handed and draws its content in a Canvas rather than working the rectangle out itself.

A manifest is untrusted input, so a bad one is skipped and reported in the Plugins debug window rather than crashing the app.

The host discovers plugins beside its own executable, from the <plugin id>.plugin.json manifests the build leaves there next to the modules cargo produced. The browser and Android cannot list a directory, so they read the same manifests through a plugins.json index instead, from the bundle root and from the assets root. Every platform runs the same host: plugin_host/runtime.rs owns the runtimes, the instances they show, input, errors and restarting, and a platform only implements its Backend - starting a runtime, exchanging messages with it, and handing over the frame it drew. There are two: plugin_host/wasm.rs runs the module under wasmtime on every platform but the browser, and plugin_host/web.rs runs the same module in a worker in the browser. A plugin runs beside the app rather than inside it either way: a thread of its own under wasmtime, a worker of its own in the browser. Neither side polls the other. Everything a plugin says arrives on its own, in the order it said it, and wakes the host; everything the host says reaches the plugin the same way.

4. Extending the protocol

If the editor needs something the host has and the plugin does not, add it to crates/block-plugin-api (a Message or EditorMessage variant, plus validate coverage and a round-trip test), accept it in the plugin's ClientSession state machine, route it in crates/block-app/src/plugin_host/instances.rs, and surface it on EditorHost or App. A message a plugin sends reaches the host by itself as long as it is not one of the session's own - the handshake, acknowledgements, errors, ping and shutdown - which Message::is_session names. Bump PROTOCOL_VERSION and describe the new rule in crates/block-plugin-api/PROTOCOL.md. Anything the host and a plugin both draw — labels, shared painting helpers — belongs in crates/block-ui, which both depend on.

5. Work that does not finish in one frame

A plugin runtime draws only when the host asks it for a frame; it paces none of that itself. When the host tells it something that changes what it shows, or something wakes it, it says a frame is needed and waits, so a burst of input or view changes it cannot keep up with is drawn as one frame carrying all of it rather than one frame each. The frame it last drew says how long it wants to wait before being drawn again, which the host holds until it comes due and then answers with a single request at the start of its own frame, so an editor animating without pause is drawn once per host frame instead of as fast as its process can run, and one the host is not drawing on screen is asked for nothing until it is on screen again. That request leaves before the host lays anything out, carrying the frame's input with it - routed against where the editor sat and what covered it the last time it was drawn - and input the host routes always brings a request with it, since input is a change the editor will want to show. The host takes whatever the runtime has published by the time it has finished building its own frame, so an editor that answers while the host is still laying out is shown in the frame that asked rather than the one after it. A message that changes nothing it draws - an acknowledgement - costs no frame. The host repaints on the same rule: a message that changes nothing it draws does not schedule a frame, and nothing about a plugin is polled. An editor doing work off the frame — the PDF editor renders its pages on a thread of its own — asks to be drawn again through ui.ctx().request_repaint() or request_repaint_after(...), which reaches the runtime's loop wherever the request came from; block_editor_plugin::Waker, which host.waker() hands out, does the same for work that has no ui to ask from. An idle editor that asks for nothing costs nothing.

A plugin that links C calling setjmp - FreeType, which beui shapes and rasterizes glyphs with - is compiled with the SjLj lowering the WASI sysroot's setjmp needs, which turns those calls into the wasm exception-handling instructions. The host runs plugins with that proposal on, so nothing about it is the plugin's business, but a module carrying a tag section is a module only a runtime with exception handling can load: `./scripts/buck run //crates/block-wasm-host:instantiate-example` is what says whether one does.

A plugin is one wasm for every platform, so a dependency it cannot have there is a dependency it cannot have at all: nothing that reaches the network (host.fetch instead), nothing that opens a file, and nothing wasm-bindgen. A dependency that only exists on some targets belongs behind a [target.'cfg(...)'.dependencies] table with a stand-in module for the rest, the way the PDF editor keeps PDFium out of its wasm build. std::thread works — the host implements thread spawning against the plugin's own shared memory — but only the plugin's first thread may talk to the GPU, and a call from any other is refused by name. A native library the plugin loads at runtime is looked for beside the app, since the app, the server and every plugin share one directory.

6. Build scripts

Nothing to edit but the editor's BUCK file, which is one `editor()` call naming the module the manifest's entry_point names (crates/editors/checklist/BUCK is the pattern). Every crate under crates/editors is staged as a plugin: `./scripts/buck run //crates/block-app:app` builds each one for wasm32-wasip1-threads with the plugin profile - its own configuration, because the app links wgpu with real backends while a guest links it with only the custom one - and lays it out beside the app with its manifest renamed <plugin id>.plugin.json, and compiles it to foo.cwasm, which opening the editor maps in rather than waiting seconds for Cranelift. The app reads foo.wasm and compiles it itself whenever the artifact is missing or was made by a different wasmtime, which is how a cross-compiled build runs. `//crates/block-app:plugins` is the plugins alone. guides/buck2.md has the rest.

7. Verification

./scripts/buck run //:verify lints every editor as the wasm guest it ships as and runs its tests there. ./scripts/buck build //crates/block-app:web builds the browser's half of the bootstrap and every plugin as the guest it actually ships as. A plugin can be driven without a GUI: ./scripts/buck run //crates/block-wasm-host:instantiate-example -- "$(./scripts/buck build //crates/editors/foo:module --show-full-output | tail -1 | cut -d' ' -f2)" takes it through the handshake, opens an instance, asks for a frame and fails unless it presented a surface.

An editor that draws with the GPU rather than with beui's own shapes uses a beui::Viewport holding a Drawing (guides/beui.md): the gpu work sits behind a Draw the beui renderer runs while it paints, and a headless test, which builds no renderer, never opens a device. A snapshot never holds what it drew, so a test of one asserts on the block and on what the editor paints around it.

A plugin never learns where its pixels live. It asks for a render target and is handed an opaque texture, which under wasmtime is a texture the app already owns in its own device — nothing is exported or imported — and in the browser is the swapchain texture of the worker's own offscreen canvas, which the host then copies from on the GPU. Its wgpu calls reach that device over the ABI in crates/block-gpu-abi, implemented for the guest by block-gpu-guest against wgpu's custom backend, and answered by block-gpu-host, which wasmtime drives directly and the browser drives through crates/block-gpu-shim, a wasm-bindgen module the worker instantiates first and binds the plugin's imports to.
