# Internationalization, built in as if from the start

beui has no internationalization today. The work here makes it a property of
the toolkit rather than a layer on top of it. Every user-visible string is a
`Message` written with `t!`, text runs through real bidi and segmentation, layout
is logical (start and end, not left and right), and values are formatted for
the user's locale. The type system enforces each of these, so new code cannot
skip them.

The whole refactor lands in one PR: a foundation agent first, then parallel
agents (see "Order of work"). We own every line of code that runs on beui, so
call sites are migrated rather than kept compatible.

Decided:

- English is the only shipped language for now. Two pseudo-locales are the test
  of the system until a second language arrives.
- English drafts are written inline in `t!`, keyed by their text. The user's
  final copy, and later translations, are a layer kept outside the repository
  and written in a strings editor that shows where each string is used.
- Messages use our own syntax, modelled on `format!`, with language-aware
  helpers (plurals, inflection, ordinals, articles). See "Messages".
- Release builds are not considered until the app is public.
- `grapheme-segmentation` is deleted in favour of `icu_segmenter`.
- Non-Latin fonts are bundled in production, loaded on demand.
- Vertical writing is not a UI layout mode. The galley is written so a vertical
  `Text` can be added later.

Not implemented yet. Items marked **(ask)** need a decision from the user during
the work.

## What exists

- **Shaping.** HarfBuzz (`harfbuzz_rs`) shapes and FreeType rasterizes
  (`crates/beui-font-freetype`). `script_runs` splits text by script, but
  Common and Inherited characters join whatever run is in progress, and there
  is no paired-bracket handling. Each run calls `guess_segment_properties()`
  and sets no language, so direction is guessed per run and the language is
  HarfBuzz's default. Fallback works per character through a cmap lookup,
  then `FontLibrary::missing` and the system resolver (fontconfig).
- **No bidi.** `shape_galley` pushes cursors in visual order, so in RTL runs
  their byte offsets decrease. `GalleyLine::x` uses a `partition_point` that
  assumes they increase, which puts carets in Arabic and Hebrew in the wrong
  place today. `RichLayout` places runs left to right and never reorders them.
- **Line breaking.** `Builder::good` (`beui-core/src/rich.rs`) is the only rule
  for where a line may break: after ASCII whitespace, `-`, `/` or `\`. CJK and
  Thai never wrap except where wrapping is forced.
- **Start and End that mean left and right.** `TextAlign`, `Align` and
  `Justify` are named `Start`/`End`, but `RichLayout::align` and `list.rs`
  resolve them to left and right. `Placement::BelowStart`, `RightStart` and
  the `*End` variants (`beui-types/src/layer.rs`) are hard-coded to the
  anchor's left and right edges.
- **Physical sides.** `Sides { left, top, right, bottom }`, the styled
  `Padding`, `LayerEdge`, the dock's `Side` and `DockEdge`, and floating
  `Edge`.
- **Strings.** Labels are `Prop<String>`, `Memo<String>` or `&'static str`.
  `view!` bodies hold about 1,400 `label="…"`, 430 `title="…"`, 450 literal
  `<Text>` children and 120 placeholders and descriptions. There is no catalog.
- **Hard-coded English and ad-hoc formatting:**
  - month and weekday names, "AM"/"PM" and "Today"
    (`beui-components-unstyled/src/datetime.rs`, `date_time_field.rs`,
    `date_time_picker.rs`);
  - `format_number` always writes a `.` decimal point;
  - four copies of `format_duration`, byte units in
    `block-app/src/debug/plugins.rs`, and "N minutes ago" with
    `if count == 1` in `be-launcher/src/time.rs` and `be-server/src/portal.rs`;
  - `ThemeKind::name()` and the other preference names;
  - shortcut labels from `Chord::label()` ("Super+Ctrl+Alt+Shift+K") and
    `key_label`;
  - the faces on the on-screen keyboard's keys.
- **Preferences.** `ui-preferences/wit/preferences.wit` holds `theme`,
  `motion` and `canvas-touch`. They are layered System → App → Developer
  (`beui-types/src/preferences.rs`), read with `use_preferences()`, and sent to
  plugins through `preferences-watch` and `hello-accepted`. There is no locale.
- **Text editing.** `text-editor-core` classifies `Word` stops by ASCII, and
  every byte at or above 0x80 falls in one class. `UnicodeWord` and
  `VisualLine` return `None`. winit drops the preedit cursor (`Preedit(text, _)`).
- **HTML backend.** Text is DOM text, so the browser shapes and breaks it.
  `TextAlign` already maps to logical CSS. No `lang` or `dir` attribute is set.
- **Accessibility.** No node sets a language or text direction.
- **Plugin manifests.** `display_name` and template names are single strings.
- **Fonts.** `beui-fonts` embeds Inter, Hack and NotoEmoji with `include_bytes!`
  (about 1.1 MB together). They cover Latin, Greek and Cyrillic only.

## Messages

### `Message` replaces `String` for anything a user reads

`Message` is the one type for user-visible text. It replaces `Prop<String>`
and `&'static str` on every `label`, `title`, `placeholder`, `description`,
tooltip and text child: in components, menus, actions, notifications and
accessibility labels.

It has no conversion from `&str` or `String`, so a bare literal in a `view!`
does not compile. It is made in exactly two ways:

- `t!("…", args…)` for UI text;
- `Message::verbatim(s)` for user content, with `.lang(tag)` when the language
  is known.

Test ids, keys and other identifiers stay `String`.

```rust
view! {
    <Button label=t!("Save") />
    <Text>{t!("{count} {file|files} selected", count = selected_count)}</Text>
    <Text>{Message::verbatim(file_name)}</Text>
}
```

Developer-facing UI (the inspector, debug panels) uses `t!` too, so every
crate is structured the same way.

### English is written inline, as a draft

A string's English is written where it is used, the way `format!` is. There is
no catalog file in the repository and no key to invent.

- **The draft.** The text in `t!` is the agent's draft. It is what tests,
  paintings and `:dev` builds show, and it tells whoever writes the final copy
  what the string is for.
- **The key is the draft.** A string is identified by its draft text plus an
  optional context, so the code stays plain `t!("Save")`. Identical drafts
  share one copy, which is usually right: one "Cancel" everywhere.
- **Context.** When one draft means two things, the call site adds a context,
  `t!("Open", context = "state")`, as gettext's `msgctxt` does.
- **Notes.** `note = "…"` explains a draft that is not clear on its own. It is
  an argument rather than a comment, because `./scripts/verify` deletes
  comments.
- **Checked at compile time.** `t!` parses its draft the way `format!` does: an
  unknown `{name}`, an unused argument, or an argument of the wrong kind
  (number, date, message, verbatim) is a compile error at the call site.
- **Typed arguments.** Arguments are `Prop`s, so they can be reactive. A
  number, date, duration, byte size or relative time picks its formatter from
  its type, with no annotation in the message.
- **Bidi isolation.** Placeables are wrapped in FSI/PDI, so a Hebrew file name
  inside an English sentence, or the reverse, lays out correctly.
- **Reactive resolution.** A `Message` is cheap: an `Rc` of its key plus its
  argument `Prop`s. The node that shows it resolves it in an effect that reads
  the locale and the arguments.
  - Switching language re-resolves only text that shows a message. Nothing is
    rebuilt.
  - A changed argument re-formats only its own message.

### The string list

The build writes a list of every string: its draft, context and note, and
each place it is used (the file and line, the component, and the prop it feeds,
which tells a label from a tooltip from an accessibility-only name).

- **Plugins.** A plugin package carries its own list, along with any
  translations, as data. The host reads a manifest's names from it without
  instantiating the plugin. Manifest names are `t!` drafts too.
- **What the editor reads.** The strings editor (below) reads this list. It is
  the only thing the repository exposes for writing copy.

### Copy is a layer outside the repository

The user writes the final English, and later other languages. Their copy is
kept outside the repository, in a workspace or a git repository of its own,
behind a small storage interface; where is not decided yet.

- **A layer over the drafts.** Each copy is keyed by draft and context, and
  replaces the draft at runtime. A string with no copy shows its draft.
  Released English is in effect a translation of the drafts.
- **Loaded at runtime.** The app loads the copy from wherever it is kept.
  Tests, paintings and `:dev` builds never load it, so they stay deterministic.
  How release builds get it waits until the app is public.
- **Changed drafts.** When an agent rewords a draft, its copy becomes unused and
  the new draft is untranslated. The strings editor pairs them (see below).

### The strings editor

A plugin editor for writing copy, with the context to write it well:

- **Edit in the running app.** Every `Text` node knows the key of the message
  it shows. In a developer mode, Alt-clicking any text in the app, or picking it
  in the inspector, opens its string. Resolution is reactive, so an edit appears
  at once everywhere the string is used, at its real size, wrapping and clipping
  included.
- **Where it appears.** Paintings record which message keys they drew and where.
  The editor shows every painting a string appears in, highlighted, including
  states that are hard to reach by hand: errors, empty states, dialogs.
  Paintings are shown as recorded; the running app is the live preview.
- **Source context.** For each string: the components and props it feeds, the
  file and line, its draft and its note.
- **Unused and untranslated strings.** When a draft changes, the editor pairs
  the unused copy with the new untranslated string when both come from the
  same component, prop and file. It shows the two drafts as a diff next to the
  copy, so moving it across is one step, and checking it still fits happens
  then too. Unpaired unused copies are listed separately, each with the last
  painting it appeared in.
- **Sharing that does not fit.** A string used in several places shows all of
  them, so a shared copy that is wrong in one place is noticed there. Splitting
  it means adding a `context` at that call site.

### The syntax

Drafts and copy use one syntax, modelled on `format!` because that is what the
code beside it looks like, with helpers that know each language. Fluent and
MessageFormat 2 make every plural a full `select` with category names; here the
common cases are one placeable each:

```
# Forms in the language's own plural order, agreeing with the nearest number argument
{count} {file|files} selected
# ru: {count} {файл|файла|файлов}     (one|few|many, from CLDR)

# Automatic inflection from the language's noun rules plus a table of irregular words
{count} {file+} selected          # "1 file", "3 files"; {child+} → "children"

# Ordinals, articles, lists, gender, capitalization
You finished {rank:ordinal}       # 1st, 2nd, 3rd; fr: 1er, 2e
Added {a thing}                   # "an apple" / "a pear"
Shared with {people:list}         # "Ana, Bo, and Cy"
{user} replied to {user:gender his|her|their} post
{term:capitalize} is ready
```

- **Number agreement.** A form list or `+` agrees with the nearest number
  argument. `{file|files @count}` names a different one.
- **Helpers belong to languages.** Each language module provides:
  - its plural order (CLDR);
  - an inflector and a table of irregular words;
  - article and elision rules (English a/an, French `de` → `d'`);
  - ordinal suffixes;
  - case forms, in case languages.
- **What ships with English.** Positional form lists work for every language
  from the start. The English module (`+`, a/an, ordinals) ships now, and each
  other language's helpers arrive with that language.
- **The escape hatch.** A full `select`, `{count -> [one] … *[other] …}`,
  covers what no helper expresses. Every helper compiles to the same AST.
- **To review with the user first.** The user writes copy in this syntax, so a
  one-page syntax sheet goes to them for review before anything is built on it
  **(ask)**.
- **The copy check.** The strings editor rejects a copy whose arguments differ
  from its draft's, or whose form list's length differs from the language's
  plural categories.

The cost is that Pontoon, Weblate and Fluent editors cannot read the strings.
If a translation platform is ever used, its files are generated from ours.

### Pseudo-locales

Both pseudo-locales are generated from the drafts at build time and selected
through the Developer preference layer, which the inspector can switch:

- **`en-XA`** accents every letter, pads each message about 40% longer, and
  brackets it, as in `[Šåṽé·····]`. Text without brackets did not come from
  `t!`, and text that gets clipped shows up.
- **`ar-XB`** reverses each message and wraps it in RTL marks. That forces
  right-to-left layout and mirroring while the text stays readable.

## Locale

### In preferences

`preferences` and `preference-layer` in `preferences.wit` gain:

- `languages: list<string>`: the user's BCP 47 tags, in order of preference;
- regional overrides: `hour-cycle`, `first-weekday`, `measurement-system` and
  `numbering-system`.

The three layers fill them in:

- **System:**
  - winit platforms: `sys-locale`;
  - web: `navigator.languages` and the `languagechange` event;
  - Android: `Configuration.getLocales()`;
  - DRM: the settings block, or `LANG` if the block does not set it.
- **App:** a language picker in the settings editor.
- **Developer:** the pseudo-locales.

Plugins receive the record unchanged through `preferences-watch`. It is plain
data, so the protocol stays independent of any framework.

### Resolved per node

- **`use_locale()`** returns a `#[derive(Store)]` `Locale`, the same pattern as
  `use_theme()`. Its fields are the negotiated `language`, `dir`,
  `hour_cycle`, `first_weekday` and the formatters. A reader of one field does
  not wake when another changes.
- **A `locale` attribute on nodes.** Layout, shaping and accessibility need the
  language and direction, and a subtree can differ from its parent: a verbatim
  Arabic document in English UI, or an English code block in Arabic UI. So a
  base-node attribute holds a language and an optional `dir` override.
  - It is inherited through the retained tree.
  - It is resolved top-down in the layout pass that already runs, so a full
    layout stays O(n).
  - `use_locale()` in a component reads its nearest ancestor's value.
- **Verbatim text.** `Message::verbatim(s).lang(tag)` sets the language for that
  run alone. Verbatim text with no tag gets `dir=auto`: the paragraph's first
  strong character decides its direction.

## Logical layout

### Types

Each of these replaces its physical form; the physical form is removed, not
kept beside it:

| Today | Becomes |
|---|---|
| `Sides { left, top, right, bottom }`, styled `Padding` | `Sides { start, top, end, bottom }` |
| `Placement::RightStart`, `LayerEdge::{Left, Right}` | `Placement::AfterStart`, `LayerEdge::{Start, End}` |
| dock `Side::{Left, Right}`, `DockEdge`, `DockAlign` → `"left"` | `Start` / `End` |
| floating `Edge::TopEnd` | resolved against `dir`, as its name already says |

Vertical stays physical. UI geometry belongs to the screen, not to the flow of
text: toolbars, docks, screen-edge bars, scrollbars, sliders and splitters. That
is why vertical scripts turn horizontal on computers.

### Mirroring

- **Converted once, at placement.** The layout engine computes each child's
  inline position against its resolved `dir`, and converts it to physical as it
  places the child: in RTL, `x = parent_inner_width - x - w`.
- **Everything after layout stays physical.** `Rect`, painting, hit testing,
  damage, the display list and the renderers are unchanged. A change of
  direction is just a full relayout.
- **Scrolling.** Scroll offsets become logical: 0 is the inline start. The
  vertical scrollbar goes on the inline-end side, which is the left in RTL, as
  in browsers.
- **Pointer geometry.** Code that reads `local.x` (slider, splitter, resize
  handles) goes through one `inline_offset(local, size)` helper.
- **HTML backend.**
  - `Sides` becomes `padding-inline-start` and `padding-inline-end`.
  - Flex already follows `dir`.
  - `lang` and `dir` attributes are written where the resolved value changes.
  - The browser then does the mirroring, shaping, bidi and line breaking.
- **Icons.** The lucide list gets a curated `mirrors` flag for each glyph:
  chevrons, arrows, undo/redo, indent, reply, back. `Icon` flips a flagged
  glyph in an RTL node. Glyphs that name a physical direction (text-align-left,
  panel-left) are not flagged.
- **Dock layouts.** Saved layouts store logical sides, so a layout saved in
  English opens mirrored in Arabic. If a frozen format keeps them
  (guides/frozen_formats.md), the logical sides are added to it, not swapped in.

### Navigation keys

- **Arrow keys become intent.** Focus dispatch turns `ArrowLeft` and
  `ArrowRight` into `Nav::Backward` and `Nav::Forward` from the focused node's
  resolved `dir`, before components see them.
- **Who reads `Nav`.** Tree expand and collapse, menu submenus, sliders and
  steppers, tabs, the dock, and every other handler of horizontal arrows (74
  files match `ArrowLeft|ArrowRight` today).
- **The exception.** Text editing keeps the physical keys, because carets move
  visually.
- **Back gesture.** The edge swipe (`BackEdge`) is mirrored too.

## Text engine

### Itemization and shaping

Each paragraph goes through these steps in order:

1. **Bidi.** Run the bidi algorithm (`unicode-bidi`), with the paragraph
   direction from the node, or `auto`.
2. **Script runs.** Split by script, resolving Common and Inherited characters
   from their neighbours, with paired-bracket handling.
3. **Language runs.** Split by the span's resolved `lang`.
4. **Font runs.** Split by which face covers each character.
5. **Shaping.** Call HarfBuzz with an explicit direction, script and language,
   in place of `guess_segment_properties`. The language turns on `locl`
   features: Serbian Cyrillic forms, the Turkish i, CJK regional glyphs.

### The galley

- **Logical clusters, visual runs.** Clusters are kept in logical order, and
  each line carries visual runs with their bidi levels.
- **Mapping positions.** `GalleyLine::x` and `index_at` map between logical and
  visual through the runs. This replaces the `partition_point` in
  `GalleyLine::x` and the same assumption in `breakpoint`, both of which expect
  x to grow with byte offset.
- **Carets and selection.** A caret has an affinity and splits where the
  direction changes. A selection is a set of visual rectangles.
- **No x or y internally.** The galley, line breaker and caret geometry use
  inline and block advances. A vertical-rl/lr `writing_mode` on `Text` can then
  be added later for content (Japanese novels, vertical headings, traditional
  Mongolian). It would need HarfBuzz top-to-bottom shaping with `vert`, UAX #50
  orientation and vertical carets. It is not part of this plan.

### Line breaking and segmentation

- **Line breaks.** UAX #14 through `icu_segmenter`. Bidi reordering runs per
  line, after the breaks are chosen. `Builder::good` is deleted.
  `WrapAt::Anywhere` stays and breaks between graphemes.
- **Dictionaries.** Thai, Lao, Khmer and Burmese need `icu_segmenter`'s LSTM or
  dictionary data (a few hundred KB). CJK word selection needs the CJK
  dictionary (several MB). Both are loaded only when that text is present. CJK
  line breaking needs no dictionary.
- **One segmentation stack.** `crates/grapheme-segmentation` is deleted.
  Graphemes, words and sentences all come from `icu_segmenter`.
- **Logical alignment and ellipsis.** `TextAlign::Start` and `End` resolve
  against the paragraph's direction. Ellipsis cuts at the visual end of the line
  in its reading direction.

### Fonts

- **Fallback depends on language.** The fallback key becomes `(char, lang)`, so
  Han characters pick a Japanese, Chinese or Korean face to match the span.
  - The fontconfig query takes the language.
  - The plugin runtime's fallback (`beui-platform-plugin/src/fonts.rs`) uses
    the same key.
- **What is bundled.** Noto Sans for Arabic, Hebrew, Devanagari, Thai and the
  other common scripts (a few hundred KB each), and Noto Sans CJK. A CJK face
  covers Japanese, Simplified and Traditional Chinese and Korean through its
  `locl` feature, given the language from shaping (verify **(ask)** if it
  doesn't).
- **Loaded on demand.** Noto Sans CJK is about 16–20 MB per weight, so the new
  faces are not `include_bytes!`. They become assets loaded on the first
  fallback miss:
  - **native:** files beside the binary;
  - **web:** `@font-face` with `unicode-range`;
  - **plugins:** fonts come from the host, never embedded in a plugin.
- **Tests.** Tests load the same files from the repository, so paintings of
  non-Latin text are deterministic.

### Editing

- **Visual caret movement.** Arrow keys move visually through bidi text using
  the galley's runs. Home and End go to the line's logical ends. `VisualLine`
  is implemented on the galley.
- **Two kinds of word.** A code editor and prose need different stops, and the
  content's `TextLanguage` picks between them, not the key:
  - **`Token`** (today's `Word`, renamed) for code: runs of identifier
    characters, runs of punctuation, and whitespace. An identifier character is
    Unicode `XID_Continue` (UAX #31), not ASCII, so `naïve_count` stays one
    token.
  - **`Word`** (today's `UnicodeWord`, implemented) for prose: UAX #29 plus the
    dictionaries. It applies to Markdown, plain and rich text, and every
    single-line field (labels, search, rename).
- **Where they apply.** Ctrl+Arrow, Ctrl+Backspace, double-click and
  `word_around` resolve to one or the other.
- **Later refinement.** A code language could use `Word` inside comments and
  strings, from the highlighter's scopes.
- **IME preedit.** The preedit cursor is kept on every platform and drawn.
  Preedit is shown even when the focused node has no `on_ime` handler.

## Formatting: `beui::intl`

Everything here is built on ICU4X and is available both as typed message
arguments and as standalone `Message`s:

- `Number`, `Percent`, `Bytes`, `Duration`, `Date`, `Time`, `DateTime`,
  `RelativeTime`, `List`;
- `Collator`, for sorting user-visible lists (the file tree, the workspace
  index);
- case-folded matching, for search and the command palette.

It replaces:

- the English in `datetime.rs`, `date_time_field.rs` and `date_time_picker.rs`;
- every `format_duration`, the byte units, and both "N minutes ago" helpers;
- `format_number`, and the parsing in the number input, which becomes
  locale-aware too.

`HourCycle` and the calendar's `first_weekday` default to the locale's values.

**Where ICU data lives.** ICU4X data is postcard-serialized Rust, read only by a
compatible ICU4X version, so it stays out of the plugin protocol. That protocol
carries the locale preferences, plus plain data any language can read: fonts,
and each plugin's string list. Rust plugins share one copy of the ICU4X data
through the shared library they link: the SDK today, or `base` once
plans/plugin_libraries.md lands. A plugin in another language uses its own i18n
library. A host formatting service for such plugins can be added when one needs
it. Segmentation never goes through it, because it runs in layout's hot path.

## Shortcuts and accessibility

- **`ShortcutLabel` component.** It replaces `shortcut: Prop<String>` in menus
  and the command palette.
  - **macOS:** lucide `ICON_COMMAND`, `ICON_OPTION` and `ICON_ARROW_BIG_UP`
    spans, then the key.
  - **Elsewhere:** localized words ("Strg+S").
  - **The key** is shown as the character the user's keyboard layout produces
    for it.
  - **Accessibility label:** always words ("Command S").
- **Bindings.** Matching by logical key with a fallback to the physical key
  stays as it is; that is already right for non-Latin layouts.
- **On-screen keyboard.** Its key faces are `t!` strings.
- **accesskit.** Nodes get `language` and `text_direction` wherever the resolved
  value changes, and labels are resolved `Message`s. The plugin accesskit
  mirror already carries both fields.

## Tests

- **Test setup.** `DocumentTest` and the editor tests get `.with_locale(…)`.
- **Pseudo-locale sweeps.** The beui-demo page sweep and `app-tests` run under
  `en-XA` and `ar-XB`. `Document::overflows` already fails a test on clipped
  text, so a message that grows too long fails.
- **Paintings.** Arabic, Hebrew, Thai and CJK wrapping, carets and selection;
  mirrored menus, popovers, the dock and sliders; a `ShortcutLabel` on macOS and
  elsewhere.
- **Unit tests.** Each message helper: plural order, the English inflector and
  irregular words, a/an, ordinals, lists.
- **`t!` checks.** Compile-fail tests for an unknown argument, an unused one,
  and one of the wrong kind.
- **The string list.** A test that the build's list holds each string's draft,
  context, note and call sites, and that paintings record the keys they drew.

## Order of work

1. **Foundation (one agent, first).**
   - `Message`, `t!` with its compile-time checks, the message parser and
     evaluator with the English helpers, and `Message::verbatim`;
   - the string list the build writes, and the storage interface for copy;
   - `Locale` in `preferences.wit`, `use_locale()`, and the node `locale`
     attribute;
   - logical `Sides`, `Placement`, `LayerEdge` and dock `Side`, and `Nav`;
   - the ICU4X crates added to the third-party build.

   These are the types and APIs, with behaviour stubbed, so everything compiles
   against them.
2. **In parallel.**
   - **Text engine:** bidi, segmentation, HarfBuzz language and direction,
     language-aware fallback, galley runs, ellipsis, on-demand fonts. Deletes
     `grapheme-segmentation`.
   - **Layout mirroring:** the conversion at placement, scrolling, layers and
     the dock, logical CSS with `lang` and `dir` in the HTML backend, icon
     mirroring.
   - **Editing and input:** visual carets, `Token` and `Word`, the IME preedit
     cursor, `Nav` in focus dispatch and every component, `ShortcutLabel`.
   - **`beui::intl`:** the formatters, replacing the ad-hoc helpers, collation,
     the date and number components, ICU data in the shared library.
   - **String migration, split by crate group** (beui crates; block-app and its
     siblings; editors): each literal becomes a `t!` draft, with a `context`
     where one draft means two things, or `Message::verbatim` for user data. Once `&str` no longer converts
     to a `Message`, the compiler lists every site.
   - **Platforms and protocol:** a locale source on each platform, the plugin
     `preferences`, localized manifests, accesskit language and direction, and
     the language picker in settings.
   - **Strings editor:** the plugin editor, editing in the running app, message
     keys recorded in paintings, and pairing unused copy with changed drafts.
3. **Integration (one agent, last).**
   - the pseudo-locales, paintings, and the pseudo-locale sweeps;
   - a new `guides/i18n.md`, and updates to `guides/beui.md`,
     `guides/plugin_sdk.md` and `guides/testing_a_gui.md`.
